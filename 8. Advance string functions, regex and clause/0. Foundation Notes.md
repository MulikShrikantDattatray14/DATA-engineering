## String functions: clean, inspect, extract, combine, format

A string function changes or inspects one text value. It does not automatically group rows or remove duplicates. Use a function in `SELECT` to show a calculated value; use an expression in `WHERE` to decide which rows survive. These examples use SQLite unless another engine is explicitly named.

Our running value is `'  mIRA.PATEL@example.com  '`: two spaces at each end, mixed letter case, and a recognizable separator. Single quotes delimit text in SQL; the quotes themselves are not part of the value. Write an apostrophe inside text twice, as in `'Mira''s account'`.

### Clean the text before using positions

`TRIM` removes spaces from both ends, `LTRIM` from the left, and `RTRIM` from the right. `LOWER` and `UPPER` change letter case. Read nested functions from the inside outward: first trim, then lowercase.

```sql
-- SQLite
SELECT
    TRIM('  mIRA.PATEL@example.com  ') AS trimmed,
    LOWER(TRIM('  mIRA.PATEL@example.com  ')) AS cleaned,
    UPPER('mira') AS uppercase;
```

| trimmed | cleaned | uppercase |
|---|---|---|
| mIRA.PATEL@example.com | mira.patel@example.com | MIRA |

Additional small checks:

| SQLite query | Result | What it shows |
|---|---|---|
| `SELECT LTRIM('  Mira  ');` | `'Mira  '` | Right-side spaces remain |
| `SELECT RTRIM('  Mira  ');` | `'  Mira'` | Left-side spaces remain |
| `SELECT TRIM('  Mira  Patel  ');` | `'Mira  Patel'` | Internal spaces remain |
| `SELECT REPLACE('Mira.Patel', '.', ' ');` | `'Mira Patel'` | Replace every matching substring |
| `SELECT REPLACE('ID-ID-7', 'ID-', '');` | `'7'` | Empty replacement deletes matches |
| `SELECT RTRIM('bosscoderxyxzyyy', 'xyz');` | `'bosscoder'` | Remove any trailing x, y, or z |

The optional second argument to SQLite trimming functions is a **set of characters**, not an exact word. Default trimming removes ordinary spaces, not every possible whitespace character; tabs and line breaks need explicit handling. Built-in SQLite case conversion handles ASCII letters; do not assume it normalizes every language. [SQLite core functions](https://www.sqlite.org/lang_corefunc.html)

SQL Server supports ordinary `TRIM(text)` from 2017; use `LTRIM(RTRIM(text))` on older versions. Its custom form is `TRIM('xyz' FROM text)`. SQL Server 2022 with compatibility level 160 adds the optional character argument to `RTRIM` and the `LEADING`/`TRAILING`/`BOTH` forms of `TRIM`. [TRIM](https://learn.microsoft.com/en-us/sql/t-sql/functions/trim-transact-sql?view=sql-server-ver17), [RTRIM](https://learn.microsoft.com/en-us/sql/t-sql/functions/rtrim-transact-sql?view=sql-server-ver17)

MySQL `TRIM('xy' FROM text)` instead removes repeated exact `xy` pieces from the ends. Its `RTRIM` accepts one argument; the two-argument classroom example is not MySQL syntax.

### Inspect: length and separator positions

Cleaning first avoids counting unwanted boundary spaces or extracting from the wrong position.

```sql
-- SQLite
SELECT
    LENGTH('  mIRA.PATEL@example.com  ') AS raw_length,
    LENGTH(TRIM('  mIRA.PATEL@example.com  ')) AS clean_length,
    INSTR(TRIM('  mIRA.PATEL@example.com  '), '@') AS at_position,
    INSTR('mira.patel@example.com', '#') AS missing_position;
```

| raw_length | clean_length | at_position | missing_position |
|---|---|---|---|
| 26 | 22 | 11 | 0 |

These positions start at **1**. In the cleaned text, the local part occupies positions 1-10, `@` is at 11, and the domain begins at 12. A missing separator produces zero; check that before calculating substring positions for unknown input.

Length names are not portable:

| Engine | Character length | Byte length | Example |
|---|---|---|---|
| SQLite | `LENGTH(text)` counts Unicode code points for ordinary text | `LENGTH(CAST(text AS BLOB))` measures encoded bytes | `LENGTH('A ')` returns 2 |
| MySQL | `CHAR_LENGTH(text)` or `CHARACTER_LENGTH(text)` | `LENGTH(text)` | With UTF-8, `CHAR_LENGTH('é')` is 1 and `LENGTH('é')` is 2 |
| SQL Server | `LEN(text)` **excludes trailing spaces** | `DATALENGTH(text)` | `LEN('A ')` returns 1 |

Bytes and characters are different measurements. A displayed symbol can also contain multiple Unicode code points, so character length is not always the number of symbols a person sees. Do not substitute byte length when the requirement asks about letters. [MySQL length functions](https://dev.mysql.com/doc/refman/8.4/en/string-functions.html#function_char-length), [SQL Server LEN](https://learn.microsoft.com/en-us/sql/t-sql/functions/len-transact-sql?view=sql-server-ver17)

SQL Server uses `CHARINDEX('@', text)` instead of SQLite's `INSTR(text, '@')`; notice the reversed argument order. `CHARINDEX('@', 'mira.patel@example.com')` returns 11. An optional third argument is the starting search position. [CHARINDEX](https://learn.microsoft.com/en-us/sql/t-sql/functions/charindex-transact-sql?view=sql-server-ver17)

For an ASCII code check, `SELECT ASCII('A');` returns 65 in MySQL and SQL Server. SQLite uses `SELECT UNICODE('A');`, also 65. ASCII covers only a limited character set; it is not a general Unicode code-point function. [SQL Server ASCII](https://learn.microsoft.com/en-us/sql/t-sql/functions/ascii-transact-sql?view=sql-server-ver17)

### Extract only the part you need

`SUBSTR(text, start, length)` means: begin at this character and take this many characters. The third argument is a **length**, not an ending position. SQLite also accepts `SUBSTRING` as an alias on versions 3.34 and newer.

```sql
-- SQLite
SELECT
    SUBSTR('mira.patel@example.com', 1, 10) AS local_part,
    SUBSTR('mira.patel@example.com', 12) AS domain,
    SUBSTR('mira.patel@example.com', -3) AS ending;
```

| local_part | domain | ending |
|---|---|---|
| mira.patel | example.com | com |

Omitting SQLite's length takes the rest of the text. A negative start counts backward from the right. For a variable separator position, calculate that position first rather than hard-coding 11:

```sql
-- SQLite: one running example, with intermediate steps visible
WITH cleaned AS (
    SELECT LOWER(TRIM('  mIRA.PATEL@example.com  ')) AS email
), located AS (
    SELECT email, INSTR(email, '@') AS at_position
    FROM cleaned
)
SELECT
    email,
    SUBSTR(email, 1, at_position - 1) AS local_part,
    SUBSTR(email, at_position + 1) AS domain
FROM located
WHERE at_position > 0;
```

| email | local_part | domain |
|---|---|---|
| mira.patel@example.com | mira.patel | example.com |

This demonstrates extraction; it is not a complete email validator. The `- 1` excludes the separator from the left piece; `+ 1` skips it for the right piece.

| Need | SQLite | SQL Server | Result for `'example.com'` |
|---|---|---|---|
| First 7 characters | `SUBSTR(text, 1, 7)` | `LEFT(text, 7)` | example |
| Last 3 characters | `SUBSTR(text, -3)` | `RIGHT(text, 3)` | com |
| 3 characters from position 2 | `SUBSTR(text, 2, 3)` | `SUBSTRING(text, 2, 3)` | xam |

SQL Server's widely supported form supplies all three `SUBSTRING` arguments. `LEFT` and `RIGHT` are also built into MySQL, but are not standard SQLite built-ins. [SQLite substring documentation](https://www.sqlite.org/lang_corefunc.html#substr)

### Combine values and decide how missing values behave

In SQLite, `||` joins text:

```sql
-- SQLite
SELECT 'Mira' || ' ' || 'Patel' AS full_name;
```

Result: `Mira Patel`. Concatenation assembles columns or expressions within a row; it does not combine multiple table rows into one list.

An empty string `''` is known text with zero characters. `NULL` means missing or unknown. `COALESCE` chooses the first non-NULL value; it does not replace empty strings.

```sql
-- SQLite
SELECT
    LENGTH('') AS empty_length,
    LENGTH(NULL) AS unknown_length,
    'Mira' || NULL AS missing_join,
    'Mira' || COALESCE(NULL, '') AS handled_join,
    COALESCE('', 'unknown') AS still_empty;
```

| empty_length | unknown_length | missing_join | handled_join | still_empty |
|---|---|---|---|---|
| 0 | NULL | NULL | Mira | `''` |

`CONCAT` and `CONCAT_WS` were added to SQLite 3.44.0. Older learning platforms can still use `||` with explicit `COALESCE`. [SQLite 3.44 release notes](https://www.sqlite.org/releaselog/3_44_0.html)

| Expression | SQLite 3.44+ | SQL Server | MySQL |
|---|---|---|---|
| `CONCAT('Mira', ' ', 'Patel')` | Mira Patel | Mira Patel | Mira Patel |
| `CONCAT('Mira', NULL, 'Patel')` | MiraPatel | MiraPatel | NULL |
| `CONCAT_WS('-', 'Mira', NULL, 'Patel')` | Mira-Patel | Mira-Patel | Mira-Patel |
| `CONCAT_WS('-', 'Mira', '', 'Patel')` | Mira--Patel | Mira--Patel | Mira--Patel |

`WS` means “with separator.” NULL values are skipped in `CONCAT_WS`, but empty strings remain, which explains the double dash. SQL Server supports `CONCAT_WS` from 2017; its `CONCAT` treats NULL arguments as empty text. [SQL Server CONCAT](https://learn.microsoft.com/en-us/sql/t-sql/functions/concat-transact-sql?view=sql-server-ver17), [CONCAT_WS](https://learn.microsoft.com/en-us/sql/t-sql/functions/concat-ws-transact-sql?view=sql-server-ver17)

### Format for display after calculating

`ROUND` keeps a numeric result. Formatting produces text and can force visible zeros or symbols. Keep values numeric while calculating and sorting numerically.

| Engine | Query | Result |
|---|---|---|
| SQLite | `SELECT PRINTF('%.2f%%', 98.1);` | `'98.10%'` |
| SQL Server | `SELECT FORMAT(98.1, 'N2', 'en-US') + '%';` | `'98.10%'` |
| MySQL | `SELECT CONCAT(FORMAT(98.1, 2, 'en_US'), '%');` | `'98.10%'` |

SQLite's `%f` formats a decimal value, `.2` requests two fractional digits, and `%%` emits a literal percent sign. `FORMAT` became an alias for SQLite `PRINTF` in 3.38.0; it does not use SQL Server's `'N2'` syntax. SQL Server's culture argument controls presentation. [SQLite formatting](https://www.sqlite.org/printf.html), [SQLite 3.38 release notes](https://www.sqlite.org/releaselog/3_38_0.html), [SQL Server FORMAT](https://learn.microsoft.com/en-us/sql/t-sql/functions/format-transact-sql?view=sql-server-ver17)

### MySQL-oriented reference from the class material

These are small reference examples, not portable SQLite queries. Use the equivalent column when practicing another engine.

| Purpose | MySQL query | Exact result | SQLite / SQL Server direction |
|---|---|---|---|
| Lowercase alias | `SELECT LCASE('MIRA');` | mira | Both: `LOWER` |
| Substring alias | `SELECT MID('bosscoder', 6, 3);` | ode | SQLite: `SUBSTR`; SQL Server: `SUBSTRING` |
| Locate from a position | `SELECT LOCATE('a', 'banana', 3);` | 4 | SQL Server: `CHARINDEX('a', 'banana', 3)` |
| Alternate position syntax | `SELECT POSITION('@' IN 'a@b.com');` | 2 | SQLite: `INSTR`; SQL Server: `CHARINDEX` |
| Pad left to a total length | `SELECT LPAD('bosscoder', 12, '0');` | 000bosscoder | Numeric SQLite example: `PRINTF('%04d', 7)` gives 0007 |
| Pad right to a total length | `SELECT RPAD('bossc', 8, '0');` | bossc000 | SQL Server can combine `REPLICATE` with text |
| Repeat | `SELECT REPEAT('ab', 3);` | ababab | SQL Server: `REPLICATE('ab', 3)`; SQLite has no built-in `REPEAT` |
| Generate spaces | `SELECT CONCAT('[', SPACE(3), ']');` | `'[   ]'` | SQL Server: `SPACE(3)`; SQLite: `PRINTF('%3s', '')` |
| Reverse | `SELECT REVERSE('Mira');` | ariM | SQL Server: same; SQLite has no built-in `REVERSE` |
| Locate a comma-list item | `SELECT FIND_IN_SET('b', 'a,b,c');` | 2 | No same-name SQLite/SQL Server built-in; prefer rows for stored collections |
| Compare strings | `SELECT STRCMP('beta', 'alpha');` | 1 | Other engines: comparisons or `CASE`; `ORDER BY` handles sorting |

`LOCATE`'s third argument is where searching starts, not the occurrence number. `FIND_IN_SET` returns a list position, not a character position; a missing item returns 0. `STRCMP` returns -1, 0, or 1. Padding lengths are total lengths, and MySQL padding can truncate an already longer input. `LPAD('bosscoder', 12, '0')` has three zeros; `RPAD('bossc', 8, '0')` really returns `bossc000`. [MySQL string function reference](https://dev.mysql.com/doc/refman/8.4/en/string-functions.html)

Collation defines comparison and sorting rules, including case and accent sensitivity. Do not assume a query's alphabetic ordering is identical on every database. Test the required behavior explicitly when case or language matters. For revision, ask: **What text do I have, what exact piece or format do I need, and what should happen for NULL or a missing separator?**

## Pattern matching: LIKE and regular expressions

### Start with the kind of match you need

Use `=` for an exact value, `LIKE` for a simple text pattern, and regex when the rule involves character types, repetition, or alternatives. A pattern is a description of acceptable text; it does not change the stored data.

| Need | LIKE pattern | Example that matches | Example that does not |
| --- | --- | --- | --- |
| Starts with `Pro` | `'Pro%'` | `Pro`, `Product` | `MyPro` |
| Ends with `box` | `'%box'` | `box`, `Toolbox` | `boxer` |
| Contains `red` | `'%red%'` | `red`, `redwood` | `blue` |
| Exactly one character after `A` | `'A_'` | `A7` | `A`, `A77` |
| Exactly three characters | `'___'` | `SQL` | `SQL2` |

`%` means zero or more characters. `_` means exactly one character. `LIKE` patterns cover the whole value: add `%` where extra characters are allowed. A dot is an ordinary character in `LIKE`; it has a special meaning in regex.

**SQLite example: a literal percent sign**

```sql
SELECT 'Save 10%' LIKE '%10!%' ESCAPE '!' AS matches;
```

Result: `1`. The first `%` is a wildcard; `!%` means an actual percent sign. Similarly, `!_` means an actual underscore. Default SQLite `LIKE` ignores ASCII letter case; SQL Server and MySQL behavior depends on collation. Do not assume a capital letter in a pattern automatically enforces uppercase. [SQLite LIKE documentation](https://www.sqlite.org/lang_expr.html#like)

### Check the database before using regex

| Engine | What to remember |
| --- | --- |
| SQLite core | `REGEXP` calls an application-defined function. No default `regexp()` implementation is supplied; an extension or application may add one. |
| MySQL 8.0/8.4 | Native `REGEXP_LIKE`, `REGEXP_REPLACE`, and `REGEXP_SUBSTR`; matching uses ICU. |
| SQL Server 2022 and earlier | These native regex functions are unavailable. `LIKE`/`PATINDEX` use SQL wildcard patterns, not full regex. |
| SQL Server 2025 | Native regex uses RE2. `REGEXP_LIKE` needs database compatibility level 170 or above; the other scalar regex functions are available at all compatibility levels. |

These are engine-specific features. The regex SQL below is labelled MySQL or SQL Server, not plain SQLite. [SQLite REGEXP](https://www.sqlite.org/lang_expr.html#regexp), [MySQL regex functions](https://dev.mysql.com/doc/refman/8.4/en/regexp.html), [SQL Server platform support](https://learn.microsoft.com/en-us/sql/t-sql/functions/regexp-like-transact-sql?view=sql-server-ver17#platform-support)

### Learn regex in small pieces

The following examples use ordinary single-line ASCII text and case-sensitive matching. For whole-value checks, `^` and `$` surround the rule. Without anchors, a matching part inside a longer value can be enough.

| Symbol | Meaning | Pattern | Matches | Does not match |
| --- | --- | --- | --- | --- |
| `^` | Start of text | `^AB` | `AB12` | `XAB12` |
| `$` | End of text | `12$` | `AB12` | `AB123` |
| `[ABC]` | One listed character | `^[ABC]$` | `B` | `D`, `AB` |
| `[A-Z]` | One uppercase ASCII letter | `^[A-Z]$` | `Q` | `q`, `QQ` |
| `[0-9]` | One ASCII digit | `^[0-9]$` | `7` | `77`, `A` |
| `[^0-9]` | One character that is not a digit | `^[^0-9]$` | `A`, `!` | `7` |
| `.` | One character, normally excluding a line break | `^h.t$` | `hat`, `h7t` | `ht`, `heat` |
| `[.]` | An actual dot | `^a[.]b$` | `a.b` | `axb` |
| `*` | Zero or more repetitions | `^ab*$` | `a`, `ab`, `abb` | `b` |
| `+` | One or more repetitions | `^ab+$` | `ab`, `abb` | `a` |
| `?` | Zero or one repetition | `^colou?r$` | `color`, `colour` | `colouur` |
| `{n}` | Exactly n repetitions | `^[0-9]{3}$` | `007` | `07`, `0007` |
| `{n,}` | At least n repetitions | `^a{2,}$` | `aa`, `aaaa` | `a` |
| `{n,m}` | Between n and m repetitions | `^a{2,4}$` | `aa`, `aaaa` | `a`, `aaaaa` |
| `\|` | Either alternative | `^(cat\|dog)$` | `cat`, `dog` | `catfish` |
| `( )` | Group a sequence | `^(ha)+$` | `ha`, `haha` | `haa` |

A quantifier applies to the item immediately before it: `ab+` repeats `b`; `(ab)+` repeats `ab`. `^` outside brackets anchors the start, while `^` immediately after `[` negates that character class. `[A-Za-z0-9_]` allows one letter, digit, or underscore; add `+` to allow a nonempty sequence.

`^cat|dog$` means starts with `cat` **or** ends with `dog`. Grouping changes it to `^(cat|dog)$`, which accepts exactly either whole word. The table escapes `|` only for Markdown display; the SQL pattern contains an ordinary pipe.

### Build a pattern from a sentence

Rule: **a product code must contain two uppercase ASCII letters, a hyphen, and three digits**.

1. Two letters: `[A-Z]{2}`.
2. Follow with the literal hyphen and digits: `[A-Z]{2}-[0-9]{3}`.
3. Require the entire value: `^[A-Z]{2}-[0-9]{3}$`.

| Input | Match? | Reason |
| --- | --- | --- |
| `AB-007` | Yes | Every part follows the rule |
| `XY-900` | Yes | Every part follows the rule |
| `ab-007` | No | Lowercase letters |
| `A-007` | No | Only one letter |
| `AB-07` | No | Only two digits |
| `XAB-007` | No | Extra leading character |
| `AB-007X` | No | Extra trailing character |
| empty string | No | Required characters are missing |

**MySQL 8 example**

```sql
SELECT REGEXP_LIKE('AB-007', '^[A-Z]{2}-[0-9]{3}$', 'c') AS matches;
```

Expected result: `1`. `'c'` explicitly requests case-sensitive matching. For SQL Server 2025 at compatibility 170+, use the Boolean condition in `CASE`:

```sql
SELECT CASE
    WHEN REGEXP_LIKE('AB-007', '^[A-Z]{2}-[0-9]{3}$', 'c')
    THEN 1 ELSE 0
END AS matches;
```

Expected result: `1`. These examples are documentation-checked; no MySQL or SQL Server instance was used to execute them.

### Search, replace, or extract

These examples work with MySQL 8 and SQL Server 2025. The argument lists shown are the forms needed here; optional arguments can differ between engines.

| Task | SQL expression | Expected output |
| --- | --- | --- |
| Keep only digits | `REGEXP_REPLACE('+91 (20) 555-0100', '[^0-9]', '')` | `91205550100` |
| Replace digit runs | `REGEXP_REPLACE('Box 12, Shelf 34', '[0-9]+', '#')` | `Box #, Shelf #` |
| Extract first number | `REGEXP_SUBSTR('Box 12, Shelf 34', '[0-9]+')` | `12` |
| Extract second number | `REGEXP_SUBSTR('Box 12, Shelf 34', '[0-9]+', 1, 2)` | `34` |
| No matching number | `REGEXP_SUBSTR('Box', '[0-9]+')` | `NULL` |

For example:

```sql
SELECT REGEXP_SUBSTR('Box 12, Shelf 34', '[0-9]+', 1, 2) AS second_number;
```

`1` is the starting character position; `2` selects the second match. `REGEXP_SUBSTR` returns the matched text, so `34` is a string here. `REGEXP_REPLACE` defaults to replacing all matches in both engines; its occurrence argument can select one instead. Replacing with `''` removes text; replacing with `' '` inserts a space. [MySQL signatures and defaults](https://dev.mysql.com/doc/refman/8.4/en/regexp.html), [SQL Server replacement](https://learn.microsoft.com/en-us/sql/t-sql/functions/regexp-replace-transact-sql?view=sql-server-ver17), [SQL Server extraction](https://learn.microsoft.com/en-us/sql/t-sql/functions/regexp-substr-transact-sql?view=sql-server-ver17)

### Escaping, word boundaries, and dialect differences

A regex `\.` matches a literal dot, but SQL must first parse the string containing that regex. With normal MySQL backslash handling, write `'\\.'`; in a SQL Server string, write `'\.'`. MySQL's `NO_BACKSLASH_ESCAPES` mode changes this. For a dot, `'[.]'` avoids that extra escaping layer. SQL quotation marks still need SQL escaping: an apostrophe inside a single-quoted string is written `''`. [MySQL string literals](https://dev.mysql.com/doc/refman/8.4/en/string-literals.html)

| Pattern concept | Example match | Example nonmatch |
| --- | --- | --- |
| `\bcat\b`: word boundaries around `cat` | `a cat!` | `scatter` |
| `\Bcat`: no word boundary immediately before `cat` | `scatter` | `cat` |
| `(ab)\1`: repeat the captured text, in engines that support pattern backreferences | `abab` | `abac` |

A word boundary is a position, not an actual space. A punctuation mark may form a boundary too. SQL Server's RE2 word characters are ASCII letters, digits, and underscore; ICU can behave differently for Unicode text. In a normal MySQL SQL literal, the first pattern becomes `'\\bcat\\b'`. [RE2 syntax](https://github.com/google/re2/wiki/Syntax), [ICU regex syntax](https://unicode-org.github.io/icu/userguide/strings/regexp.html)

**Backreferences are not portable.** MySQL's ICU supports them, but SQL Server's RE2 does not support backreferences in matching patterns or lookaround assertions. SQL Server can still insert captured groups in a **replacement** string; that is a different operation. [RE2 unsupported constructs](https://github.com/google/re2/wiki/Syntax), [SQL Server replacement groups](https://learn.microsoft.com/en-us/sql/t-sql/functions/regexp-replace-transact-sql?view=sql-server-ver17)

### Email and URL examples: define what the pattern really proves

The supplied material uses this simplified email shape:

```text
^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+[.][A-Za-z]{2,}$
```

It accepts `sam.lee@example.com`, rejects `sam.example.com`, and rejects `sam@example`. It is **not a complete email validator**: it also accepts some unwanted structures such as `a..b@example.com`. A classroom rule, a real email specification, and a particular site's sign-up policy can be different. Build the exact rule required by the question.

The source's `@[^.]+` extracts `@example` from `sam@example.com`; that omits `.com` and includes `@`, so it is not the complete domain. For an already well-formed address, the following neutral example extracts everything after its only `@`:

```sql
-- MySQL 8 or SQL Server 2025
SELECT REGEXP_SUBSTR('sam@example.com', '[^@]+$') AS domain;
```

Expected result: `example.com`. This extracts; it does not validate the input first.

For simple URL extraction:

```sql
-- MySQL 8 or SQL Server 2025
SELECT REGEXP_SUBSTR(
    'Visit https://docs.example.com/help now',
    'https?://[^ ]+'
) AS url;
```

Expected result: `https://docs.example.com/help`. `s?` permits both `http` and `https`. `[^ ]+` stops only at a literal space; it can include tabs, newlines, or trailing punctuation. It is a simple extraction rule, not a full URL parser.

Also, `^[^.]+` applied to that URL extracts `https://docs`, not a clean subdomain. Separate the scheme and hostname before reasoning about hostname labels. The first label alone does not universally identify a subdomain.

### Pattern review habit

State the rule first; then test one valid value, one almost-valid value, an extra prefix/suffix, wrong case, an empty value, and `NULL`. Decide whether the task needs a substring match or a whole-value match, and verify the engine before choosing its regex function.

## SQL clauses: build the result in stages

A **function** calculates a value, such as `LOWER(name)`. A **clause** controls a stage of the query, such as `WHERE` or `GROUP BY`. `LIKE` is a pattern-matching operator; `AND` and `OR` combine conditions. They are not separate query clauses.

### Written order and logical order

Write a typical SQLite query in this order:

```sql
SELECT region, SUM(amount) AS total_amount
FROM Sales
WHERE sold_on >= '2026-01-01' AND sold_on < '2026-02-01'
GROUP BY region
HAVING SUM(amount) >= 100
ORDER BY total_amount DESC, region ASC
LIMIT 1;
```

Think through it as:

**FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT, if used -> ORDER BY -> LIMIT/TOP**

This describes how to reason about the result, not the physical execution plan. SQL Server puts `TOP` beside `SELECT` in written SQL. The optimizer can choose a different physical execution strategy. [Logical SELECT processing](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-transact-sql#logical-processing-order-of-the-select-statement)

### One example carried through every stage

Run this setup in an empty SQLite practice database:

```sql
CREATE TABLE Sales (
    sale_id INTEGER PRIMARY KEY,
    region TEXT,
    item TEXT,
    quantity INTEGER,
    amount INTEGER,
    sold_on TEXT
);

INSERT INTO Sales VALUES
    (1, 'East',  'Pen',  2,  40, '2026-01-05'),
    (2, 'East',  'Book', 1,  60, '2026-01-06'),
    (3, 'West',  'Pen',  1,  20, '2026-01-07'),
    (4, 'West',  'Book', 3, 180, '2026-01-08'),
    (5, 'East',  'Pen',  1,  20, '2026-02-01'),
    (6, 'North', 'Pen',  1,  20, '2026-01-10');
```

`amount` is the total sale amount for that row, not the unit price. One input row represents one sale.

| sale_id | region | item | quantity | amount | sold_on |
|---|---|---|---|---|---|
| 1 | East | Pen | 2 | 40 | 2026-01-05 |
| 2 | East | Book | 1 | 60 | 2026-01-06 |
| 3 | West | Pen | 1 | 20 | 2026-01-07 |
| 4 | West | Book | 3 | 180 | 2026-01-08 |
| 5 | East | Pen | 1 | 20 | 2026-02-01 |
| 6 | North | Pen | 1 | 20 | 2026-01-10 |

**1. FROM and SELECT: choose the source and columns.**

```sql
SELECT sale_id, region, amount
FROM Sales
ORDER BY sale_id;
```

This returns all six sales, with only those three columns. `SELECT` changes the columns displayed; it does not remove duplicate rows unless you request `DISTINCT`.

**2. WHERE: keep individual rows before calculating totals.**

```sql
SELECT sale_id, region, amount
FROM Sales
WHERE sold_on >= '2026-01-01'
  AND sold_on < '2026-02-01'
ORDER BY sale_id;
```

| sale_id | region | amount |
|---|---|---|
| 1 | East | 40 |
| 2 | East | 60 |
| 3 | West | 20 |
| 4 | West | 180 |
| 6 | North | 20 |

Sale 5 is excluded because it is on February 1. The lower boundary is included and the upper boundary is excluded. This approach also includes January 31 timestamps without inventing an end-of-day time. SQLite text dates must use a consistent sortable ISO format for these comparisons.

**3. GROUP BY: change the meaning of one result row.**

```sql
SELECT region, COUNT(*) AS sale_count, SUM(amount) AS total_amount
FROM Sales
WHERE sold_on >= '2026-01-01'
  AND sold_on < '2026-02-01'
GROUP BY region
ORDER BY region;
```

| region | sale_count | total_amount |
|---|---|---|
| East | 2 | 100 |
| North | 1 | 20 |
| West | 2 | 200 |

One row now represents a region, not a sale. East combines 40 + 60, West combines 20 + 180, and North keeps 20. Do not select an individual `sale_id` here: a group contains more than one sale. For portable SQL, every selected non-aggregate column should be grouped (or otherwise satisfy the engine's grouping rules).

**4. HAVING: filter the completed groups.**

```sql
SELECT region, SUM(amount) AS total_amount
FROM Sales
WHERE sold_on >= '2026-01-01'
  AND sold_on < '2026-02-01'
GROUP BY region
HAVING SUM(amount) >= 100
ORDER BY region;
```

| region | total_amount |
|---|---|
| East | 100 |
| West | 200 |

North is excluded. `WHERE amount >= 100` would instead discard small individual sales before grouping; that would lose East entirely and give West only 180. **Use WHERE for row conditions and HAVING for group totals.**

**5. ORDER BY: arrange the result.**

Changing the last line to `ORDER BY total_amount DESC, region ASC` puts West first, then East. The second expression breaks ties. `GROUP BY` alone is not a sorting promise. Without an `ORDER BY`, result order is unspecified. [SQLite SELECT and ordering](https://www.sqlite.org/lang_select.html)

**6. LIMIT or TOP: keep a chosen number of rows.**

The complete SQLite query at the beginning keeps only West, with `total_amount = 200`. `LIMIT 1` means one row, not every row tied for first place.

SQL Server equivalent, with `sold_on` stored as a `DATE` or `DATETIME` column containing the same dates:

```sql
SELECT TOP (1) region, SUM(amount) AS total_amount
FROM Sales
WHERE sold_on >= '20260101' AND sold_on < '20260201'
GROUP BY region
HAVING SUM(amount) >= 100
ORDER BY total_amount DESC, region ASC;
```

### Conditions, duplicates, NULLs and arithmetic

| Need | Example | Meaning / result on Sales |
|---|---|---|
| Both conditions | `region = 'East' AND amount >= 40` | Sales 1 and 2 |
| Either condition | `region = 'East' OR region = 'West'` | Sales 1, 2, 3, 4, 5 |
| A set of values | `region IN ('East', 'West')` | Same rows as the OR example |
| Group alternatives | `(region = 'East' OR region = 'West') AND amount >= 40` | Sales 1, 2, 4 |
| Simple text pattern | `item LIKE 'B%'` | Book sales 2 and 4 |
| Inclusive endpoints | `amount BETWEEN 40 AND 60` | Sales 1 and 2 |
| Missing value | `region IS NULL` | No rows in this example; never write `= NULL` |
| Distinct displayed values | `SELECT DISTINCT region FROM Sales ORDER BY region;` | East, North, West |

`AND` binds more tightly than `OR`; parentheses express the intended grouping. [SQL Server operator precedence](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/operator-precedence-transact-sql)

A `WHERE` condition keeps rows where the expression is true. An unknown result, such as comparing a NULL to a value, is not kept. `NULL` means missing/unknown; `''` is an empty string. Use `COALESCE(value, replacement)` only when a replacement matches the question's meaning.

| Aggregate | What it counts or calculates |
|---|---|
| `COUNT(*)` | All rows in the group |
| `COUNT(column)` | Rows where that column is not NULL |
| `COUNT(DISTINCT column)` | Different non-NULL values |
| `SUM(amount)` | Sum of non-NULL amounts |
| `AVG(amount)` | Average of non-NULL amounts |

SQLite example:

```sql
SELECT
    COUNT(*) AS rows_seen,
    COUNT(item) AS named_items,
    COUNT(DISTINCT item) AS different_items,
    SUM(amount) AS revenue,
    ROUND(AVG(amount), 2) AS average_sale
FROM Sales;
```

| rows_seen | named_items | different_items | revenue | average_sale |
|---|---|---|---|---|
| 6 | 6 | 2 | 340 | 56.67 |

In SQL Server, `AVG` over an integer column returns an integer. Use `ROUND(AVG(1.0 * amount), 2)` for the decimal average shown above. [SQL Server AVG return types](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql)

For a percentage, count the qualifying rows, divide by the relevant total, then multiply by 100:

```sql
SELECT ROUND(
    100.0 * SUM(CASE WHEN quantity >= 2 THEN 1 ELSE 0 END)
    / COUNT(*), 2
) AS bulk_sale_percentage
FROM Sales;
```

Result: `33.33`, because sales 1 and 4 qualify: 2 out of 6. The decimal `100.0` prevents integer division. An empty population needs a deliberately chosen result; `NULLIF(denominator, 0)` prevents division by zero. Decide whether a missing result should remain NULL or become zero.

For portable SQL, use SELECT aliases in `ORDER BY`, but avoid relying on them in `WHERE`; repeat the expression or put it in a CTE/subquery. Some engines, including SQLite, allow extra alias uses that SQL Server rejects.

## Joining text across rows

`CONCAT` joins values within one row. A text aggregate combines values from several rows into one string. First decide whether repeated values should remain, then decide the order inside the string.

Example input: `Pune`, `Delhi`, `Pune`. Keeping repetitions would produce `Delhi, Pune, Pune`. Keeping distinct cities produces `Delhi, Pune`.

SQLite 3.44 or later:

```sql
WITH Places(city) AS (
    VALUES ('Pune'), ('Delhi'), ('Pune')
), UniqueCities AS (
    SELECT DISTINCT city FROM Places
)
SELECT GROUP_CONCAT(city, ', ' ORDER BY city) AS cities
FROM UniqueCities;
```

| cities |
|---|
| Delhi, Pune |

SQL Server 2017 or later, with database compatibility level 110 or later for the ordering clause:

```sql
WITH Places AS (
    SELECT city
    FROM (VALUES ('Pune'), ('Delhi'), ('Pune')) AS V(city)
), UniqueCities AS (
    SELECT DISTINCT city FROM Places
)
SELECT STRING_AGG(city, ', ') WITHIN GROUP (ORDER BY city) AS cities
FROM UniqueCities;
```

MySQL form for a table containing the same city values:

```sql
SELECT GROUP_CONCAT(DISTINCT city ORDER BY city SEPARATOR ', ') AS cities
FROM Places;
```

The outer `ORDER BY` sorts result rows; the aggregate's own ordering sorts values inside each string. These are separate jobs. These aggregates ignore NULL inputs. SQL Server does not support `STRING_AGG(DISTINCT ...)`; remove duplicates in a prior query, as above. Older SQLite versions reject the inline aggregate `ORDER BY`: check `SELECT sqlite_version();` before using this syntax. [SQLite aggregate functions](https://www.sqlite.org/lang_aggfunc.html), [SQLite 3.44 release](https://www.sqlite.org/releaselog/3_44_0.html), [SQL Server STRING_AGG](https://learn.microsoft.com/en-us/sql/t-sql/functions/string-agg-transact-sql), [MySQL GROUP_CONCAT](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html#function_group-concat)

## Supporting number and date functions from the class slide

These functions support filtering and presentation, but are not string functions themselves.

| Task | SQLite example | SQL Server example | Expected value |
|---|---|---|---|
| Round a number | `ROUND(12.3456, 2)` | `ROUND(12.3456, 2)` | 12.35 |
| Add five days | `DATE('2026-01-28', '+5 days')` | `CAST(DATEADD(day, 5, '20260128') AS date)` | 2026-02-02 |
| Date-only day difference | `JULIANDAY('2026-02-02') - JULIANDAY('2026-01-28')` | `DATEDIFF(day, '20260128', '20260202')` | 5 days |
| Year | `STRFTIME('%Y', '2026-02-03')` | `YEAR('20260203')` | '2026' in SQLite; 2026 in SQL Server |
| Month | `STRFTIME('%m', '2026-02-03')` | `MONTH('20260203')` | '02' in SQLite; 2 in SQL Server |
| Day | `STRFTIME('%d', '2026-02-03')` | `DAY('20260203')` | '03' in SQLite; 3 in SQL Server |
| Current timestamp | `DATETIME('now')` | `GETDATE()` | Changes at execution time |

Each expression can be run as `SELECT expression;`. In MySQL, `NOW()` returns the current date/time. SQLite `DATETIME('now')` uses UTC; SQL Server `GETDATE()` uses the database system's clock without a time-zone offset. These are not automatically the learner's local time. [SQLite date functions](https://www.sqlite.org/lang_datefunc.html), [SQL Server GETDATE](https://learn.microsoft.com/en-us/sql/t-sql/functions/getdate-transact-sql)

`DATEDIFF` counts boundaries of the requested date part, not always complete elapsed units. For example, SQL Server `DATEDIFF(day, '2026-01-01T23:59:00', '2026-01-02T00:01:00')` is 1, although only two minutes passed. The Julian-day subtraction in the table matches the date-only example; it is not a general translation of every `DATEDIFF` use. [SQL Server DATEDIFF](https://learn.microsoft.com/en-us/sql/t-sql/functions/datediff-transact-sql)

`ROUND` returns a number. It does not guarantee that a result grid will display trailing zeros. Formatting functions return text for display; keep numeric values numeric while doing calculations.

## Quick revision sheet

| Situation | First thing to remember |
|---|---|
| Text has unwanted spaces | `TRIM` affects ends; internal spaces need a separate rule |
| Need part of a string | Find the starting position, then decide the length |
| Need the portion after a separator | Locate the separator; verify it exists before adding 1 |
| Need character count | Check the engine: SQLite `LENGTH`, SQL Server `LEN`, MySQL `CHAR_LENGTH` |
| Join text from columns | Concatenate within a row; decide what NULL means |
| Join text from many rows | Use a text aggregate; decide duplicates and internal ordering |
| Simple prefix / suffix / contains | `LIKE 'x%'`, `LIKE '%x'`, `LIKE '%x%'` |
| Fixed text structure | Build regex pieces and use anchors when the entire value must match |
| Dot or underscore in a pattern | Their meaning depends on LIKE versus regex and escaping |
| Count missing matches | `COUNT(*)` counts rows; `COUNT(nullable_column)` skips NULLs |
| Filter before totals | `WHERE` |
| Filter based on totals | `HAVING` |
| Need decimals | Use decimal arithmetic before rounding; check integer `AVG` behavior |
| Need a complete month | Include the first day; exclude the first day of the next month |
| Need only a few rows | Sort first, define tie handling, then `LIMIT` / `TOP` |
| Need visible trailing zeros | Numeric rounding and text formatting are separate tasks |

### Source corrections worth remembering

- `LENGTH` does not mean bytes in every engine: it counts characters for SQLite text but bytes in MySQL.
- The third argument to `LOCATE` is a starting search position, not an occurrence number.
- `MID('bosscoder', 6, 3)` returns `ode`; `RPAD('bossc', 8, '0')` returns `bossc000`.
- `TRIM` syntax and custom-character behavior differ across engines; copying a mixed-dialect example can fail.
- `@[^.]+` does not return a complete email domain, and `^[^.]+` does not reliably extract a subdomain from a URL.
- Regex support is not universal. In particular, ordinary SQLite does not ship a default regex function, and older SQL Server releases lack the new native regex functions.
- A short email or URL regex checks the rule it describes; it does not prove every real-world address or URL is valid.
- `LIKE`, `AND`, and `OR` are operators used inside expressions, not independent SQL clauses.
