# Advanced SELECT - Quick Revision Notes

**Main idea:** define exactly which rows qualify and what each output value should be.

Read in this order: **filter -> handle missing values -> calculate -> remove duplicates -> order -> limit -> combine result sets**.

Use the optional scratch setup at the end. It reuses Section 0's Products data, so the same rows support each idea. Queries use SQLite; SQL Server differences are labelled. The examples are small demonstrations rather than assignment answers.

## 1. Start with an output contract

Before writing a clause, state the required columns, what one output row represents, and the ordering. This section starts with one output row per selected product.

```sql
SELECT product_id, product_name, category, price_cents, stock
FROM Products ORDER BY product_id;
```

**Result:**

| product_id | product_name | category | price_cents | stock |
| --- | --- | --- | --- | --- |
| 1 | Pen | Stationery | 200 | 10 |
| 2 | Notebook | Stationery | 500 | 0 |
| 3 | Mug | Home | 800 | NULL |
| 4 | Bottle | Home | 800 | 5 |
| 5 | Pen | Stationery | 200 | 20 |


Two different products are named Pen. A name match can legitimately return both. The product key is product_id, stock 0 is known zero, and NULL stock is unknown.

| Clause | Role |
|---|---|
| SELECT | Choose and calculate output values |
| FROM | Choose the input |
| WHERE | Keep rows meeting the condition |
| DISTINCT | Remove duplicate selected rows |
| ORDER BY | Sort by one or more expressions |
| LIMIT in SQLite | Keep a portion of the sorted rows |

A SELECT without DISTINCT keeps qualifying source rows even if their displayed values repeat. Do not add DISTINCT just to hide a row-count mistake. If a problem asks for individual products, keep their IDs when needed to distinguish them.

Use aliases for readable output: AS changes a result-column label, not the underlying stored name. Avoid relying on a SELECT alias in WHERE; repeat the expression or create a separate query level.

## 2. Comparisons, IN and BETWEEN

| Test | Meaning |
|---|---|
| = | Equal |
| <> | Not equal |
| > / < | Strictly above / below |
| >= / <= | Inclusive bound |
| IN (...) | Equals any listed value |
| BETWEEN low AND high | Includes both endpoints |
| IS NULL / IS NOT NULL | Missing / present value |

```sql
SELECT product_id, product_name, price_cents
FROM Products
WHERE price_cents BETWEEN 200 AND 500
ORDER BY product_id;
```

**Result:**

| product_id | product_name | price_cents |
| --- | --- | --- |
| 1 | Pen | 200 |
| 2 | Notebook | 500 |
| 5 | Pen | 200 |


BETWEEN 200 AND 500 includes products priced at both 200 and 500 cents. For “more than 500,” use > 500; for “at least 500,” use >= 500. Read the wording before choosing the operator.

```sql
SELECT product_id, product_name
FROM Products
WHERE product_id IN (1, 3, 5)
ORDER BY product_id;
```

**Result:**

| product_id | product_name |
| --- | --- |
| 1 | Pen |
| 3 | Mug |
| 5 | Pen |


IN matches whole values, not patterns. For several patterns, write a complete LIKE comparison on each side of OR. Avoid quoting numeric columns just to make a comparison succeed; keep values consistent with their intended types.

### Date intervals

For an entire month, a lower inclusive and upper exclusive range is easy to check:

```sql
SELECT event_id, event_date
FROM DateEvents
WHERE event_date >= '2020-02-01'
  AND event_date < '2020-03-01'
ORDER BY event_id;
```

**Result:**

| event_id | event_date |
| --- | --- |
| 2 | 2020-02-01 |
| 3 | 2020-02-29 |


The interval includes February 1 and leap day, while excluding January 31 and March 1. For real timestamps, the same boundary shape includes every time on the last day without guessing a last second.

SQLite's example stores consistent zero-padded ISO dates as text. Text order matches chronological date order in this representation; arbitrary formats such as 2/1/2020 do not have that property. SQL Server applications normally use DATE or DATETIME2 instead of VARCHAR for dates.

BETWEEN is inclusive at both ends. For timestamps, BETWEEN '2020-02-01' AND '2020-02-29' may include only midnight at the upper endpoint, not all of February 29.

## 3. AND, OR and parentheses

SQL evaluates NOT before AND, and AND before OR. Use parentheses to make the intended groups visible.

Suppose we want products in Home or Stationery **and also** positive stock.

```sql
SELECT product_id, product_name
FROM Products
WHERE category = 'Home'
   OR category = 'Stationery' AND stock > 0
ORDER BY product_id;
```

**Result:**

| product_id | product_name |
| --- | --- |
| 1 | Pen |
| 3 | Mug |
| 4 | Bottle |
| 5 | Pen |


Without parentheses, the expression means Home OR (Stationery AND positive stock). Mug is included merely because it is Home, even though its stock is unknown.

```sql
SELECT product_id, product_name
FROM Products
WHERE (category = 'Home' OR category = 'Stationery')
  AND stock > 0
ORDER BY product_id;
```

**Result:**

| product_id | product_name |
| --- | --- |
| 1 | Pen |
| 4 | Bottle |
| 5 | Pen |


Now the positive-stock condition applies to both categories, leaving products 1, 4 and 5.

| A | B | A AND B | A OR B |
|---|---|---|---|
| True | True | True | True |
| True | False | False | True |
| False | True | False | True |
| False | False | False | False |

This table assumes non-NULL truth values. NULL adds UNKNOWN: TRUE OR UNKNOWN is TRUE, while FALSE OR UNKNOWN is UNKNOWN. WHERE discards both FALSE and UNKNOWN.

The written order of conditions is not a reliable error guard. Instead of hoping denominator <> 0 is evaluated before a division, make the division safe with NULLIF.

## 4. NULL, COALESCE and safe calculations

NULL means a value is absent; it is not zero. A filter stock <> 0 also excludes NULL stock because the comparison is unknown. To include missing stock explicitly, use stock <> 0 OR stock IS NULL.

```sql
SELECT product_id, product_name,
       COALESCE(CAST(stock AS VARCHAR(10)), 'unknown') AS stock_display
FROM Products ORDER BY product_id;
```

**Result:**

| product_id | product_name | stock_display |
| --- | --- | --- |
| 1 | Pen | 10 |
| 2 | Notebook | 0 |
| 3 | Mug | unknown |
| 4 | Bottle | 5 |
| 5 | Pen | 20 |


COALESCE returns the first non-NULL expression. Here we first convert known stock to text so that the alternate text 'unknown' has a compatible type in SQL Server. This is a display choice; it does not change stored stock.

### CASE: choose an output value

```sql
SELECT product_id, product_name,
       CASE
           WHEN stock IS NULL THEN 'Unknown'
           WHEN stock = 0 THEN 'Sold out'
           ELSE 'Available'
       END AS availability
FROM Products ORDER BY product_id;
```

**Result:**

| product_id | product_name | availability |
| --- | --- | --- |
| 1 | Pen | Available |
| 2 | Notebook | Sold out |
| 3 | Mug | Unknown |
| 4 | Bottle | Available |
| 5 | Pen | Available |


CASE checks conditions in order and uses the first true branch. Start with a special missing-value check when it matters. ELSE covers remaining rows; omitting ELSE gives NULL when no condition is true. CASE creates a value; it does not remove rows.

A simple CASE compares one expression to values, such as CASE category WHEN 'Home' THEN 'H' ELSE 'S' END. A searched CASE, as above, can express ranges and IS NULL conditions.

### NULLIF: prevent an undefined rate

```sql
WITH Metrics AS (
    SELECT 3 AS orders, 20 AS visits
    UNION ALL
    SELECT 0, 0
)
SELECT orders, visits,
       ROUND(orders * 100.0 / NULLIF(visits, 0), 2) AS conversion_rate
FROM Metrics ORDER BY visits DESC;
```

**Result:**

| orders | visits | conversion_rate |
| --- | --- | --- |
| 3 | 20 | 15 |
| 0 | 0 | NULL |


NULLIF(visits, 0) returns NULL for a zero denominator. That produces a missing rate rather than a divide-by-zero error in SQL Server. The 20-visit example gives 3 / 20 * 100 = 15.

COALESCE(rate, 0) is optional business logic: use it only if an undefined rate really should be displayed as zero. Do not silently turn “no observations” into a measured 0%.

```sql
SELECT product_id,
       price_cents * 1.0 / 100 AS price,
       ROUND(price_cents * 0.9 / 100, 2) AS discounted_price
FROM Products WHERE product_id <= 2
ORDER BY product_id;
```

**Result:**

| product_id | price | discounted_price |
| --- | --- | --- |
| 1 | 2 | 1.8 |
| 2 | 5 | 4.5 |


Multiplying by 1.0 before integer division preserves the fraction. ROUND(...,2) rounds the numeric value; presentation may still show 1.8 instead of 1.80. Parentheses should reflect the intended numerator and denominator, especially in percentages and weighted averages.

Do not use NOT IN when its candidate list/subquery can contain NULL without examining the consequences. For example, 5 NOT IN (1, NULL) is UNKNOWN, not TRUE. For missing relationships, NOT EXISTS often states the requirement more safely; the joins and subqueries sections explain that pattern.

## 5. LIKE and literal pattern characters

LIKE compares an entire string with a pattern. In SQLite, % matches zero or more characters and _ matches exactly one character.

```sql
SELECT product_id, product_name
FROM Products
WHERE product_name LIKE 'P%' OR product_name LIKE '%oo%'
ORDER BY product_id;
```

**Result:**

| product_id | product_name |
| --- | --- |
| 1 | Pen |
| 2 | Notebook |
| 5 | Pen |


P% finds names beginning with P; %oo% finds names containing oo. Together they return both Pens and Notebook.

| Need | Pattern | Example |
|---|---|---|
| Begins with Pen | 'Pen%' | Pen, Pencil |
| Ends with book | '%book' | Notebook |
| Contains ot | '%ot%' | Bottle |
| Exactly three characters | '___' | Pen, Mug |
| Literal percent sign | '10!%' ESCAPE '!' | 10% |

```sql
SELECT CASE WHEN '10%' LIKE '10!%' ESCAPE '!'
            THEN 'match' ELSE 'no match' END AS literal_percent;
```

**Result:**

| literal_percent |
| --- |
| match |


SQLite LIKE ignores ASCII letter case by default, but not every Unicode case difference. SQL Server LIKE depends on collation and also supports bracket sets; SQLite LIKE treats brackets literally. SQLite GLOB uses different symbols (* and ?) and is case-sensitive. Do not interchange these dialect rules. [SQLite pattern matching](https://www.sqlite.org/lang_expr.html#the_like_glob_regexp_match_and_extract_operators)

For deeper string slicing, date functions and regular expressions, use [Section 8's notes](<../8. Advance string functions, regex and clause/0. Foundation Notes.md>).

## 6. DISTINCT, sorting and NULL placement

```sql
SELECT DISTINCT category
FROM Products
ORDER BY category;
```

**Result:**

| category |
| --- |
| Home |
| Stationery |


DISTINCT compares the complete selected row. SELECT DISTINCT category returns two categories; selecting category and product_id would retain all five products because the pairs differ. Duplicate removal and sorting are separate operations.

```sql
SELECT product_id, product_name, price_cents
FROM Products
ORDER BY price_cents DESC, product_name ASC, product_id ASC;
```

**Result:**

| product_id | product_name | price_cents |
| --- | --- | --- |
| 4 | Bottle | 800 |
| 3 | Mug | 800 |
| 2 | Notebook | 500 |
| 1 | Pen | 200 |
| 5 | Pen | 200 |


Rows are sorted by price descending, then product_name ascending, then ID ascending. The final ID breaks any remaining ties predictably. ASC is the default direction; specify DESC separately for each column that needs it.

Collation affects how text is sorted and compared, including case and accents. Do not assume every database has the same alphabetic rules.

To put missing stock last in a portable way:

```sql
SELECT product_id, stock
FROM Products
ORDER BY CASE WHEN stock IS NULL THEN 1 ELSE 0 END,
         stock ASC, product_id ASC;
```

**Result:**

| product_id | stock |
| --- | --- |
| 2 | 0 |
| 4 | 5 |
| 1 | 10 |
| 5 | 20 |
| 3 | NULL |


The CASE assigns known stock a sort key of 0 and missing stock 1. Known values are then ordered by stock, and product_id resolves ties. This states the requirement instead of relying on an engine's default NULL placement.

ORDER BY is what guarantees output order. Neither a primary key nor DISTINCT is an implicit sorting promise.

## 7. Top rows, ties and pagination

### Return a fixed number of rows

```sql
SELECT product_id, product_name, price_cents
FROM Products
ORDER BY price_cents DESC, product_id
LIMIT 2;
```

**Result:**

| product_id | product_name | price_cents |
| --- | --- | --- |
| 3 | Mug | 800 |
| 4 | Bottle | 800 |


SQLite LIMIT 2 keeps exactly two rows when at least two qualify. The unique ID tie-breaker determines which products come first among equal prices.

SQL Server uses TOP:
```sql
SELECT TOP (2) product_id, product_name, price_cents
FROM Products
ORDER BY price_cents DESC, product_id;
```


This is a SQL Server-only syntax adaptation, reviewed rather than executed here. It selects the same two product rows. Without ORDER BY, neither TOP nor LIMIT identifies a meaningful “highest” or “first” group.

### Keep all rows tied at a boundary

For the highest price in this dataset, both Mug and Bottle cost 800:

```sql
SELECT product_id, product_name, price_cents
FROM Products
WHERE price_cents = (SELECT MAX(price_cents) FROM Products)
ORDER BY product_id;
```

**Result:**

| product_id | product_name | price_cents |
| --- | --- | --- |
| 3 | Mug | 800 |
| 4 | Bottle | 800 |


SQL Server can express a top-row boundary with SELECT TOP (1) WITH TIES ... ORDER BY price_cents DESC. Ties are defined by **all** ORDER BY expressions: adding product_id would remove the price tie. For the top N distinct prices, use a distinct-value ranking approach instead. These are different requirements. [SQL Server TOP and ties](https://learn.microsoft.com/en-us/sql/t-sql/queries/top-transact-sql?view=sql-server-ver17)

### Skip a page of ordered rows

```sql
SELECT product_id, product_name
FROM Products
ORDER BY product_id
LIMIT 2 OFFSET 2;
```

**Result:**

| product_id | product_name |
| --- | --- |
| 3 | Mug |
| 4 | Bottle |


This skips the first two product IDs and returns the next two. The SQL Server equivalent is:
```sql
SELECT product_id, product_name
FROM Products
ORDER BY product_id
OFFSET 2 ROWS FETCH NEXT 2 ROWS ONLY;
```


A unique, stable ordering is essential. If data changes between page requests, OFFSET pagination can still skip or repeat rows; sorting alone does not freeze the dataset. For large or changing result sets, keyset pagination (for example, IDs after the last returned ID) can be preferable. [SQL Server OFFSET/FETCH](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-order-by-clause-transact-sql?view=sql-server-ver17)

## 8. Combine result sets with set operators

A join attaches columns by matching rows. A set operator combines or compares complete result rows vertically.

Here query A returns categories of products costing at least 500 cents: Stationery, Home, Home. Query B returns categories of products with stock at least 10: Stationery, Stationery.

```sql
SELECT category FROM Products WHERE price_cents >= 500
UNION
SELECT category FROM Products WHERE stock >= 10
ORDER BY category;
```

**Result:**

| category |
| --- |
| Home |
| Stationery |


UNION combines the results and removes duplicate rows.

```sql
SELECT category FROM Products WHERE price_cents >= 500
UNION ALL
SELECT category FROM Products WHERE stock >= 10
ORDER BY category;
```

**Result:**

| category |
| --- |
| Home |
| Home |
| Stationery |
| Stationery |
| Stationery |


UNION ALL preserves repetitions: two Home rows from A and three Stationery rows across A and B. Use it when every contributing row matters.

```sql
SELECT category FROM Products WHERE price_cents >= 500
INTERSECT
SELECT category FROM Products WHERE stock >= 10
ORDER BY category;
```

**Result:**

| category |
| --- |
| Stationery |


INTERSECT keeps distinct rows appearing in both results.

```sql
SELECT category FROM Products WHERE price_cents >= 500
EXCEPT
SELECT category FROM Products WHERE stock >= 10
ORDER BY category;
```

**Result:**

| category |
| --- |
| Home |


EXCEPT keeps distinct rows in the first result that do not appear in the second. Reversing the two queries changes its meaning.

| Operator | Duplicate rule | Result here |
|---|---|---|
| UNION | Distinct combined rows | Home, Stationery |
| UNION ALL | Keep all rows | Home twice, Stationery three times |
| INTERSECT | Distinct shared rows | Stationery |
| EXCEPT | Distinct left-only rows | Home |

The SELECT branches must return the same number of columns in corresponding positions, with compatible types. Columns match by position, not by alias. The first branch supplies the output names. Apply the final ORDER BY to the combined result.

SQLite and SQL Server support these four forms; do not assume INTERSECT ALL or EXCEPT ALL is available. Avoid mixing different set operators without making grouping explicit through subqueries/CTEs: precedence rules differ between engines. [SQLite compound SELECT](https://www.sqlite.org/lang_select.html#compound_select_statements)

## 9. Quick revision

| Wording in a question | Likely expression |
|---|---|
| At least / at most | >= / <= |
| Strictly greater / less | > / < |
| Either condition | OR |
| Both conditions | AND |
| Missing value | IS NULL |
| First available value | COALESCE |
| Conditional label/value | CASE |
| Undefined division | NULLIF(denominator,0) |
| Different selected rows | DISTINCT |
| Preserve every combined row | UNION ALL |
| Common rows | INTERSECT |
| First result excluding second | EXCEPT |

Five checks: parentheses match the intended logic; NULL behavior is intentional; numerator/denominator and decimal arithmetic are correct; selected columns match the output contract; ordering includes the required tie-breakers before limiting.

Use parameters for values supplied by an application instead of building SQL strings from user input. Parameter syntax varies by client library; values and SQL identifiers are different things.

## Optional: create the example tables

Run this once in a fresh scratch database before trying the examples in order. The table definitions and inserts below also work in SQL Server. In SQLite, enable `PRAGMA foreign_keys = ON;` for the connection if you want foreign keys enforced.

```sql
CREATE TABLE Suppliers (
    supplier_id INT NOT NULL PRIMARY KEY,
    supplier_name VARCHAR(40) NOT NULL
);
CREATE TABLE Products (
    product_id INT NOT NULL PRIMARY KEY,
    product_name VARCHAR(40) NOT NULL,
    category VARCHAR(30) NOT NULL,
    price_cents INT NOT NULL CHECK (price_cents >= 0),
    stock INT CHECK (stock >= 0),
    supplier_id INT,
    FOREIGN KEY (supplier_id) REFERENCES Suppliers(supplier_id)
);
INSERT INTO Suppliers VALUES (1, 'Acme'), (2, 'Bright');
INSERT INTO Products VALUES
(1, 'Pen',      'Stationery', 200, 10,   1),
(2, 'Notebook', 'Stationery', 500, 0,    1),
(3, 'Mug',      'Home',       800, NULL, 2),
(4, 'Bottle',   'Home',       800, 5,    2),
(5, 'Pen',      'Stationery', 200, 20,   NULL);
CREATE TABLE DateEvents (event_id INT NOT NULL PRIMARY KEY, event_date VARCHAR(10));
INSERT INTO DateEvents VALUES
(1, '2020-01-31'), (2, '2020-02-01'),
(3, '2020-02-29'), (4, '2020-03-01');
```

*Validation: SQLite examples were executed against the sample data. SQL Server adaptations were reviewed for syntax and behavior; they were not executed on a SQL Server instance.*
