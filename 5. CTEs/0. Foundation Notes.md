# Section 5 foundation notes: Common Table Expressions (CTEs)

Use these notes to revise **how to break a SQL problem into clear intermediate results**. They combine the two supplied CTE handouts, with worked examples and corrections where the material is inconsistent. SQLite is the practice dialect; SQL Server differences are labelled.

Read in this order: **define the output -> plan intermediate rows -> write one CTE -> combine CTEs -> inspect results -> learn recursion**. Each worked example keeps its own input data throughout the steps.

## How to use this guide

| Before writing SQL, decide | Example |
|---|---|
| What does one final row represent? | One department, one user, or one employee in a hierarchy |
| What information is missing from the input rows? | A department average or a total user count |
| What should one intermediate row represent? | One department with its calculated average |
| How will the next step use those rows? | Join by department, compare values, or calculate a percentage |
| How can I check it? | Inspect the intermediate table and count rows before adding another step |

A CTE gives a step a name. You still choose the correct `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, or calculation inside that step. For example, knowing the syntax of `WITH` does not decide whether a missing match needs a `LEFT JOIN`.

## Ordinary CTEs: give each step a useful name

A Common Table Expression (CTE) is a named query result that is available within **one SQL statement**. Define the name with `WITH`, then read it in the main query of that same statement. This helps express a task as understandable steps: calculate department averages, attach the relevant average to each employee, and keep employees above it. The original table remains unchanged by these `SELECT` examples. [SQLite WITH documentation](https://www.sqlite.org/lang_with.html)

### One example for the whole chapter

The article's employee names and reporting relationships are retained below. **Departments and salaries are invented teaching values because the original table screenshots were not included in the pasted material.** They are not claimed to be the article's missing input.

| employee_id | first_name | last_name | department | salary | manager_id |
|---|---|---|---|---|---|
| 1 | Michael | Anderson | Management | 120000 | NULL |
| 2 | Emily | Johnson | Engineering | 90000 | 1 |
| 3 | Daniel | Williams | Sales | 80000 | 1 |
| 4 | Sophia | Miller | Engineering | 70000 | 2 |
| 5 | Ethan | Brown | Engineering | 60000 | 2 |

One input row represents **one employee**. An employee's `manager_id` refers to another employee's `employee_id`; NULL marks someone with no manager. These relationships will remain available for later examples.

Run this setup once in a fresh SQLite database:

```sql
CREATE TABLE employees (
    employee_id INTEGER PRIMARY KEY,
    first_name TEXT NOT NULL,
    last_name TEXT NOT NULL,
    department TEXT NOT NULL,
    salary INTEGER NOT NULL,
    manager_id INTEGER
);

INSERT INTO employees (
    employee_id, first_name, last_name,
    department, salary, manager_id
) VALUES
    (1, 'Michael', 'Anderson', 'Management', 120000, NULL),
    (2, 'Emily', 'Johnson', 'Engineering', 90000, 1),
    (3, 'Daniel', 'Williams', 'Sales', 80000, 1),
    (4, 'Sophia', 'Miller', 'Engineering', 70000, 2),
    (5, 'Ethan', 'Brown', 'Engineering', 60000, 2);
```

### Read the syntax before adding calculations

The general structure is:

```text
WITH meaningful_name AS (
    query that produces the intermediate rows
)
query that consumes meaningful_name;
```

`WITH` introduces the definitions. `meaningful_name` identifies one intermediate result. `AS (...)` contains the query defining its columns and rows. The final query decides what the user receives.

The definition and the consumer are **one statement**. Put the semicolon after the final query, not immediately after the closing parenthesis. A definition by itself is incomplete. After the statement ends, a new `SELECT` cannot access that CTE unless it defines it again.

### Step 1: calculate one average per department

First describe the required intermediate row: **one department and its average salary**. That leads to `GROUP BY department` and `AVG(...)`.

```sql
WITH avg_salary_by_dept AS (
    SELECT
        department,
        AVG(1.0 * salary) AS avg_salary
    FROM employees
    GROUP BY department
)
SELECT
    department,
    ROUND(avg_salary, 2) AS avg_salary
FROM avg_salary_by_dept
ORDER BY department;
```

| department | avg_salary |
|---|---|
| Engineering | 73333.33 |
| Management | 120000 |
| Sales | 80000 |

Engineering combines Emily, Sophia, and Ethan: `(90000 + 70000 + 60000) / 3`. Management and Sales each contain one employee, so their averages equal that person's salary.

Five employee rows become three department rows. The CTE exposes only `department` and `avg_salary`; it does not expose individual employee names. To recover employee details, join it to `employees`.

`1.0 * salary` gives the average a decimal input. `ROUND` belongs to the outer display query here: the CTE still holds the unrounded average for later comparisons. A display such as `120000` is numerically the same as `120000.00`; client formatting can differ.

### Optional column list: name the intermediate columns explicitly

Instead of placing aliases beside the selected expressions, list the output names after the CTE name:

```sql
WITH dept_summary(department_name, average_salary) AS (
    SELECT department, AVG(1.0 * salary)
    FROM employees
    GROUP BY department
)
SELECT
    department_name,
    ROUND(average_salary, 2) AS average_salary
FROM dept_summary
ORDER BY department_name;
```

This produces the same three values, with headings `department_name` and `average_salary`. Names map by position: the first name belongs to the first selected expression. Use the same number of names as output expressions. The outer query must use these exposed names; it cannot refer to a different alias hidden inside the definition.

### Step 2: attach each employee's department average

Before filtering, inspect which average each employee receives:

```sql
WITH avg_salary_by_dept AS (
    SELECT department, AVG(1.0 * salary) AS avg_salary
    FROM employees
    GROUP BY department
)
SELECT
    e.employee_id,
    e.first_name,
    e.salary,
    ROUND(d.avg_salary, 2) AS department_average,
    CASE WHEN e.salary > d.avg_salary THEN 'Yes'
         ELSE 'No'
    END AS above_average
FROM employees AS e
JOIN avg_salary_by_dept AS d
    ON e.department = d.department
ORDER BY e.employee_id;
```

| employee_id | first_name | salary | department_average | above_average |
|---|---|---|---|---|
| 1 | Michael | 120000 | 120000 | No |
| 2 | Emily | 90000 | 73333.33 | Yes |
| 3 | Daniel | 80000 | 80000 | No |
| 4 | Sophia | 70000 | 73333.33 | No |
| 5 | Ethan | 60000 | 73333.33 | No |

The join compares departments because that is what one CTE row represents. Each employee matches exactly one department-summary row in this fixture, so the join keeps five rows. Joining without the department condition would compare employees with unrelated departments.

Michael and Daniel equal their department averages; “above” means strictly greater, so they do not qualify. Emily qualifies. The displayed average is rounded, but the `CASE` compares against the original unrounded value.

### Step 3: a second CTE can consume the first

Name the filtered employee rows `above_dept_average`. This makes its purpose visible before reading the final selection:

```sql
WITH avg_salary_by_dept AS (
    SELECT department, AVG(1.0 * salary) AS avg_salary
    FROM employees
    GROUP BY department
),
above_dept_average AS (
    SELECT
        e.employee_id,
        e.first_name,
        e.last_name,
        e.department,
        e.salary,
        d.avg_salary
    FROM employees AS e
    JOIN avg_salary_by_dept AS d
        ON e.department = d.department
    WHERE e.salary > d.avg_salary
)
SELECT
    employee_id,
    first_name,
    last_name,
    department,
    salary,
    ROUND(avg_salary, 2) AS department_average
FROM above_dept_average
ORDER BY employee_id;
```

| employee_id | first_name | last_name | department | salary | department_average |
|---|---|---|---|---|---|
| 2 | Emily | Johnson | Engineering | 90000 | 73333.33 |

Use **one `WITH` and a comma between definitions**. The second CTE uses the first by name; the final query consumes the second. Define dependencies first. The thinking sequence is `5 employees -> 3 department averages -> 5 comparisons -> 1 qualifying employee`. This is a logical explanation of the result, not a promise about the engine's physical execution order.

### SQL Server translation and quick checks

These ordinary CTE queries also work in SQL Server when `employees` has suitable types, such as `INT` IDs, `VARCHAR(50)` names/departments, and `DECIMAL(12,2)` salary. Use `;WITH` when the preceding statement might lack its terminating semicolon: that leading semicolon terminates the **previous** statement. Keep the CTE and its consumer together. SQL Server requires earlier CTE definitions before later references, and the optional column-name count must match the output-column count. [SQL Server CTE documentation](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql?view=sql-server-ver17)

Before running a CTE query, check each intermediate result's row meaning, output columns, join keys, and expected row count. Keep rounding in the final presentation when a later step compares numeric values. Put final ordering on the final `SELECT` so the requested output order is explicit.

## Filter first, then calculate a percentage

This classroom example asks: **among the rows at position 1 for each query name, what percentage have a good result?** It is a different metric from the rating/position quality calculation in Section 5 Question 1.

The supplied `Queries` sample is:

| query_name | result | position |
|---|---|---|
| dog | good | 1 |
| dog | bad | 2 |
| cat | good | 1 |
| cat | good | 2 |
| dog | good | 3 |
| cat | bad | 1 |

**Source clarification:** the handout says `(query_name, position)` is unique, but the sample contains two `(cat, 1)` rows. To reproduce its example, treat rows as separate observations and allow that repeated pair. Do not add a unique constraint that would reject the supplied data.

<details>
<summary>SQLite setup for this classroom example</summary>

Run in a fresh practice database so it does not conflict with the different `Queries` schema in Question 1.

```sql
CREATE TABLE Queries (
    query_name TEXT,
    result TEXT,
    position INTEGER
);

INSERT INTO Queries VALUES
    ('dog', 'good', 1),
    ('dog', 'bad', 2),
    ('cat', 'good', 1),
    ('cat', 'good', 2),
    ('dog', 'good', 3),
    ('cat', 'bad', 1);
```

</details>

### Step 1: decide which rows belong in the denominator

Both the good count and the total count must use **only position 1 rows**. First inspect that population:

```sql
SELECT query_name, result, position
FROM Queries
WHERE position = 1
ORDER BY query_name, result;
```

| query_name | result | position |
|---|---|---|
| cat | bad | 1 |
| cat | good | 1 |
| dog | good | 1 |

The two other dog observations and the cat observation at position 2 are excluded before counting. Using all original rows in the denominator would answer a different question.

### Step 2: name those rows, then count within each name

```sql
WITH first_position AS (
    SELECT query_name, result
    FROM Queries
    WHERE position = 1
)
SELECT
    query_name,
    SUM(CASE WHEN result = 'good' THEN 1 ELSE 0 END) AS good_count,
    COUNT(*) AS total_count
FROM first_position
GROUP BY query_name
ORDER BY query_name;
```

| query_name | good_count | total_count |
|---|---|---|
| cat | 1 | 2 |
| dog | 1 | 1 |

The `CASE` assigns 1 to each good observation and 0 to each other observation. `SUM` counts the good observations; `COUNT(*)` counts every observation remaining in that group. `first_position` still means one observation per row, while this grouped result means one query name per row.

### Step 3: assemble the calculation

```sql
WITH first_position AS (
    SELECT query_name, result
    FROM Queries
    WHERE position = 1
)
SELECT
    query_name,
    ROUND(
        100.0 * SUM(CASE WHEN result = 'good' THEN 1 ELSE 0 END)
        / COUNT(*),
        2
    ) AS good_query_percentage
FROM first_position
GROUP BY query_name
ORDER BY query_name;
```

| query_name | good_query_percentage |
|---|---|
| cat | 50.00 |
| dog | 100.00 |

Cat: `100.0 * 1 / 2 = 50`. Dog: `100.0 * 1 / 1 = 100`. Each emitted group contains at least one position 1 row, so its denominator is positive. A query name with no position 1 observation has no output row in this example.

The `100.0` keeps the arithmetic decimal and converts the fraction into a percentage. Round the completed ratio. Displaying exactly two trailing decimal places is a client-formatting concern; `50` and `50.00` have the same numeric value.

The handout's original query uses `WHERE` and aggregation directly. Here, a CTE names its filtering step to demonstrate the concept. Both forms express the same calculation; a simple problem does not require a CTE.

## Two independent CTEs: percentage attending each contest

These illustrative CTE examples use the attachment's samples without replacing your saved solutions. The handout says "at least one contest," but its output requires a **percentage per contest**, as in the saved [contest question](<2.Sql Percentage Of Users Attended A Contest.md>).

One output row represents one contest: participating users divided by all users. Name these two separate counts before combining them.

**Users**

| user_id | user_name |
|---|---|
| 6 | Alice |
| 2 | Bob |
| 7 | Alex |

**Register**

| contest_id | user_id |
|---|---|
| 215 | 6 |
| 209 | 2 |
| 208 | 2 |
| 210 | 6 |
| 208 | 6 |
| 209 | 7 |
| 209 | 6 |
| 215 | 7 |
| 208 | 7 |
| 210 | 2 |
| 207 | 2 |
| 210 | 7 |

### First count the population

Count users before considering individual contests. Counting registrations would give 12, which is the wrong denominator: a person may register for several contests.

```sql
WITH total_users AS (
    SELECT COUNT(*) AS total FROM Users
)
SELECT total FROM total_users;
```

| total |
|---|
| 3 |

Aggregating without grouping produces exactly one row, even for an empty Users table, where total is 0. Naming this result does not imply physical storage.

### Then count participants per contest

Group registrations by contest and count distinct user IDs. Contest/user pairs are unique here, so counting rows also works; DISTINCT makes the intended unit explicit.

```sql
WITH contest_attendance AS (
    SELECT contest_id, COUNT(DISTINCT user_id) AS attended
    FROM Register
    GROUP BY contest_id
)
SELECT contest_id, attended
FROM contest_attendance
ORDER BY contest_id;
```

| contest_id | attended |
|---|---|
| 207 | 1 |
| 208 | 3 |
| 209 | 3 |
| 210 | 3 |
| 215 | 2 |

The CTEs are independent: neither needs the other. Count all Users, including those who never register; they still belong in the denominator.

### Attach the single denominator and calculate

CROSS JOIN pairs every left row with every right row: **5 contest rows x 1 total row = 5 rows**. Every contest receives total = 3, so no matching key is needed. A two-row denominator would duplicate each contest; check both inputs' row counts.

```sql
WITH total_users AS (
    SELECT COUNT(*) AS total FROM Users
), contest_attendance AS (
    SELECT contest_id, COUNT(DISTINCT user_id) AS attended
    FROM Register
    GROUP BY contest_id
)
SELECT c.contest_id,
       ROUND(100.0 * c.attended / NULLIF(t.total, 0), 2) AS percentage
FROM contest_attendance AS c
CROSS JOIN total_users AS t
ORDER BY percentage DESC, c.contest_id ASC;
```

| contest_id | percentage |
|---|---|
| 208 | 100.00 |
| 209 | 100.00 |
| 210 | 100.00 |
| 215 | 66.67 |
| 207 | 33.33 |

Contest 215 has Alice and Alex: 100 x 2 / 3 = 66.67 after final rounding. Contest 207 has Bob: 100 x 1 / 3 = 33.33. Full-attendance contests tie at 100 and sort by ID.

The decimal 100.0 prevents integer division. NULLIF(total, 0) leaves an undefined percentage NULL. With both tables empty, no contest groups exist, so the result has no rows. ROUND does not guarantee visible trailing zeros; 100.0 and 100.00 represent the same number.

## Pattern: summarize events, then preserve every user

For [Confirmation Rate](<3.Sql Confirmation Rate.md>), signup IDs are 3, 7, 2 and 6. The seven confirmation rows are shown without their timestamps, which do not affect these counts:

| user_id | action |
|---|---|
| 3 | timeout |
| 3 | timeout |
| 7 | confirmed |
| 7 | confirmed |
| 7 | confirmed |
| 2 | confirmed |
| 2 | timeout |

Summarize requests per user, then attach counts to all signups. The confirmation_counts CTE produces:

| user_id | confirmed_count | total_count |
|---|---|---|
| 2 | 1 | 2 |
| 3 | 0 | 2 |
| 7 | 3 | 3 |

User 6 has no group here. Starting the final query from Signups and using LEFT JOIN preserves that user; an inner join would remove them.

```sql
WITH confirmation_counts AS (
    SELECT user_id,
           SUM(CASE WHEN action = 'confirmed' THEN 1 ELSE 0 END) AS confirmed_count,
           COUNT(*) AS total_count
    FROM Confirmations
    GROUP BY user_id
)
SELECT s.user_id,
       ROUND(COALESCE(1.0 * c.confirmed_count / c.total_count, 0), 2)
           AS confirmation_rate
FROM Signups AS s
LEFT JOIN confirmation_counts AS c ON s.user_id = c.user_id
ORDER BY s.user_id;
```

| user_id | confirmation_rate |
|---|---|
| 2 | 0.50 |
| 3 | 0.00 |
| 6 | 0.00 |
| 7 | 1.00 |

COUNT(*) counts actual requests inside Confirmations; each group has a positive total_count. The missing group for user 6 becomes NULL after joining, so COALESCE supplies the required zero. This **rate ranges from 0 to 1**: do not multiply by 100. ORDER BY makes the illustration easy to inspect.

## Pattern: create required combinations before attaching events

For [Students and Examinations](<4.Sql Students And Examinations.md>), Students contains (1, Alice), (2, Bob), (13, John), and (6, Alex). Subjects contains Math, Physics, and Programming. The attachment's Examinations rows are:

| student_id | subject_name |
|---|---|
| 1 | Math |
| 1 | Physics |
| 1 | Programming |
| 2 | Programming |
| 1 | Physics |
| 1 | Math |
| 13 | Math |
| 13 | Programming |
| 13 | Physics |
| 2 | Math |
| 1 | Math |

One output row must exist for every student/subject combination, even without an exam. Therefore build 4 x 3 = 12 pairs before looking at attendance. These are six of the intermediate student_subject_pairs rows:

| student_id | student_name | subject_name |
|---|---|---|
| 2 | Bob | Math |
| 2 | Bob | Physics |
| 2 | Bob | Programming |
| 6 | Alex | Math |
| 6 | Alex | Physics |
| 6 | Alex | Programming |

Alice and John supply the other six pairs. The LEFT JOIN must match both student_id and subject_name; matching just one would attach unrelated examinations.

```sql
WITH student_subject_pairs AS (
    SELECT s.student_id, s.student_name, sub.subject_name
    FROM Students AS s
    CROSS JOIN Subjects AS sub
)
SELECT p.student_id, p.student_name, p.subject_name,
       COUNT(e.student_id) AS attended_exams
FROM student_subject_pairs AS p
LEFT JOIN Examinations AS e
    ON e.student_id = p.student_id
    AND e.subject_name = p.subject_name
GROUP BY p.student_id, p.student_name, p.subject_name
ORDER BY p.student_id, p.subject_name;
```

| student_id | student_name | subject_name | attended_exams |
|---|---|---|---|
| 1 | Alice | Math | 3 |
| 1 | Alice | Physics | 2 |
| 1 | Alice | Programming | 1 |
| 2 | Bob | Math | 1 |
| 2 | Bob | Physics | 0 |
| 2 | Bob | Programming | 1 |
| 6 | Alex | Math | 0 |
| 6 | Alex | Physics | 0 |
| 6 | Alex | Programming | 0 |
| 13 | John | Math | 1 |
| 13 | John | Physics | 1 |
| 13 | John | Programming | 1 |

Duplicate examination rows represent separate attendances and must remain: Alice's three Math rows count as three. COUNT(e.student_id) counts matched events and ignores NULL in the preserved unmatched row. COUNT(*) after this LEFT JOIN would incorrectly count Bob's missing Physics exam as one.

## Pattern: select the eligible population before taking a percentage

For [Immediate Food Delivery II](<5.Sql Find Immediate Delivery Ii.md>), use the same seven deliveries throughout:

| delivery_id | customer_id | order_date | customer_pref_delivery_date |
|---|---|---|---|
| 1 | 1 | 2019-08-01 | 2019-08-02 |
| 2 | 2 | 2019-08-02 | 2019-08-02 |
| 3 | 1 | 2019-08-11 | 2019-08-12 |
| 4 | 3 | 2019-08-24 | 2019-08-24 |
| 5 | 3 | 2019-08-21 | 2019-08-22 |
| 6 | 2 | 2019-08-11 | 2019-08-13 |
| 7 | 4 | 2019-08-09 | 2019-08-09 |

First choose each customer's earliest order, then classify it. Filtering for immediate deliveries first would make customer 3's later delivery 4 look eligible and change the question.

The FirstOrders CTE retains these rows, shown in customer order:

| delivery_id | customer_id | order_date | customer_pref_delivery_date |
|---|---|---|---|
| 1 | 1 | 2019-08-01 | 2019-08-02 |
| 2 | 2 | 2019-08-02 | 2019-08-02 |
| 5 | 3 | 2019-08-21 | 2019-08-22 |
| 7 | 4 | 2019-08-09 | 2019-08-09 |

The correlated subquery finds each customer's earliest date. The guaranteed unique first order gives four eligible rows for four customers.

```sql
WITH FirstOrders AS (
    SELECT d.*
    FROM Delivery AS d
    WHERE d.order_date = (
        SELECT MIN(x.order_date)
        FROM Delivery AS x
        WHERE x.customer_id = d.customer_id
    )
), Aggregated AS (
    SELECT COUNT(*) AS total_first_orders,
           SUM(CASE WHEN order_date = customer_pref_delivery_date
                    THEN 1 ELSE 0 END) AS immediate_first_orders
    FROM FirstOrders
)
SELECT ROUND(100.0 * immediate_first_orders
             / NULLIF(total_first_orders, 0), 2) AS immediate_percentage
FROM Aggregated;
```

Aggregated contains one row:

| total_first_orders | immediate_first_orders |
|---|---|
| 4 | 2 |

The final output is:

| immediate_percentage |
|---|
| 50.00 |

Deliveries 2 and 7 are immediate: 100 x 2 / 4 = 50%. The denominator is four first orders, not seven deliveries. On empty input, COUNT(*) is 0 and SUM is NULL, yielding NULL. No empty-population result was specified, so this example leaves it undefined.

State what each intermediate row means before joining or counting it. CTEs do not automatically handle duplicates, missing rows, or denominators. ## Recursive CTEs: follow an employee hierarchy

A self-join can connect an employee to their direct manager. A recursive CTE repeats that relationship to reach further levels without writing another join for every level. We will reuse the same five employees:

```text
Michael Anderson (1)
    Emily Johnson (2)
        Sophia Miller (4)
        Ethan Brown (5)
    Daniel Williams (3)
```

Here, `manager_id` points to another row's `employee_id`. Michael's `manager_id` is `NULL`. Our result needs one row per reachable employee, their hierarchy level, and their direct manager's name.

### 1. Anchor: choose where to begin

The **anchor member** supplies the starting rows. For the whole organization, begin with employees who have no manager:

```sql
SELECT employee_id, first_name, last_name, manager_id,
       1 AS emp_level
FROM employees
WHERE manager_id IS NULL;
```

| employee_id | first_name | last_name | manager_id | emp_level |
| --- | --- | --- | --- | --- |
| 1 | Michael | Anderson | NULL | 1 |

The number `1` is our chosen level label; it is not calculated from the employee ID. An employee with ID 500 could also be at level 1.

### 2. Recursive member: find the next level

Inside the CTE, `r` represents a row already reached. Find employees whose `manager_id` matches that employee:

```sql
-- Fragment inside cte_reports, after the anchor and UNION ALL
SELECT e.employee_id, e.first_name, e.last_name, e.manager_id,
       r.emp_level + 1 AS emp_level
FROM employees AS e
JOIN cte_reports AS r
    ON e.manager_id = r.employee_id
```

For Michael, `r.employee_id = 1`, so the join finds Emily and Daniel. For Emily, it finds Sophia and Ethan. `r.emp_level + 1` places each report one level below their manager.

### 3. Trace the same data until no more rows appear

| Stage | Rows produced: employee_id, name, manager_id, emp_level |
| --- | --- |
| Anchor | `1, Michael Anderson, NULL, 1` |
| Next level | `2, Emily Johnson, 1, 2`; `3, Daniel Williams, 1, 2` |
| Next level | `4, Sophia Miller, 2, 3`; `5, Ethan Brown, 2, 3` |
| Next attempt | No rows: nobody reports to Sophia or Ethan |

`UNION ALL` preserves the anchor rows and every row found through recursion. It does not remove duplicates. Recursion finishes when no further rows can be generated. The trace is a useful way to reason about levels; SQLite actually describes its execution using a work queue, so do not rely on an implicit display order. [SQLite recursive CTE evaluation](https://www.sqlite.org/lang_with.html#recursive_common_table_expressions), [SQL Server recursive structure](https://learn.microsoft.com/en-us/sql/t-sql/queries/recursive-common-table-expression-transact-sql?view=sql-server-ver17#structure-of-a-recursive-cte)

### 4. Complete SQLite query

Run this after creating the shared `employees` fixture:

```sql
WITH RECURSIVE cte_reports (
    employee_id, first_name, last_name, manager_id, emp_level
) AS (
    SELECT employee_id, first_name, last_name, manager_id, 1
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.employee_id, e.first_name, e.last_name, e.manager_id,
           r.emp_level + 1
    FROM employees AS e
    JOIN cte_reports AS r
        ON e.manager_id = r.employee_id
)
SELECT
    r.employee_id,
    r.first_name || ' ' || r.last_name AS full_name,
    r.emp_level,
    m.first_name || ' ' || m.last_name AS manager
FROM cte_reports AS r
LEFT JOIN employees AS m
    ON r.manager_id = m.employee_id
ORDER BY r.emp_level, r.employee_id;
```

The final `LEFT JOIN` adds the manager's name **after** building the hierarchy. It keeps Michael even though he has no matching manager. An inner join here would remove him. `ORDER BY` explicitly puts lower levels first, then orders employees by ID within each level.

| employee_id | full_name | emp_level | manager |
| --- | --- | --- | --- |
| 1 | Michael Anderson | 1 | NULL |
| 2 | Emily Johnson | 2 | Michael Anderson |
| 3 | Daniel Williams | 2 | Michael Anderson |
| 4 | Sophia Miller | 3 | Emily Johnson |
| 5 | Ethan Brown | 3 | Emily Johnson |

### 5. SQL Server equivalent

SQL Server uses `WITH`, without the `RECURSIVE` keyword. The leading semicolon safely terminates a preceding statement. Both members return the same five columns, using the same underlying column types; the level starts as an integer and stays an integer. SQL Server requires corresponding anchor and recursive column types to match. The outer join stays outside the recursive member, where it is allowed. [SQL Server CTE rules](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql?view=sql-server-ver17#guidelines-for-recursive-common-table-expressions)

```sql
;WITH cte_reports (
    employee_id, first_name, last_name, manager_id, emp_level
) AS (
    SELECT employee_id, first_name, last_name, manager_id, 1
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.employee_id, e.first_name, e.last_name, e.manager_id,
           r.emp_level + 1
    FROM employees AS e
    JOIN cte_reports AS r
        ON e.manager_id = r.employee_id
)
SELECT
    r.employee_id,
    CONCAT(r.first_name, ' ', r.last_name) AS full_name,
    r.emp_level,
    CASE WHEN m.employee_id IS NULL THEN NULL
         ELSE CONCAT(m.first_name, ' ', m.last_name)
    END AS manager
FROM cte_reports AS r
LEFT JOIN employees AS m
    ON r.manager_id = m.employee_id
ORDER BY r.emp_level, r.employee_id
OPTION (MAXRECURSION 100);
```

The `CASE` preserves the root's `NULL` manager: SQL Server `CONCAT` alone would turn missing name parts into an empty-looking value. This returns the same five rows for the fixture. The SQLite query and intermediate levels were executed; this SQL Server version was reviewed against its documented syntax.

### 6. Termination and incomplete hierarchies

This example assumes unique employee IDs and a finite hierarchy without cycles. Every employee we expect to display must be reachable from a row whose `manager_id IS NULL`. Multiple roots are allowed. If the anchor finds no roots, the result is empty. An employee pointing to a nonexistent manager is not reached from a valid root.

SQL Server defaults to **100 recursive steps**. `MAXRECURSION 100` states that limit explicitly; it does not mean 100 output rows. Reaching the limit produces an error, and any partial result is not a complete hierarchy. `MAXRECURSION 0` removes the limit; it does not detect or repair a cycle. `MAXRECURSION` is not SQLite syntax. [SQL Server recursion limit](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-query?view=sql-server-ver17#maxrecursion-integer_value)

A deliberate depth condition, such as adding `WHERE r.emp_level < 2` to the recursive member, returns only Michael, Emily, and Daniel. It stops at level 2, so it is a **partial traversal**, not a complete answer for this organization.

With arbitrary starting points or graph relationships, revisiting a node can keep producing rows. SQLite allows `UNION` for recursive deduplication, but it compares whole rows: revisiting an employee at a different level or with a different path still produces a different row. It does not automatically solve every cycle. SQL Server requires `UNION ALL` between the anchor and recursive member. For this root-start employee model, a disconnected cyclic component may instead be omitted entirely. Check the data relationships as well as the stopping rule. [SQLite UNION behavior](https://www.sqlite.org/lang_with.html#recursive_common_table_expressions), [SQL Server recursive operators](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql?view=sql-server-ver17#guidelines-for-recursive-common-table-expressions)

## CTE, subquery, temporary table, or view

Choose the form that makes the task clear and provides the lifetime you need.

| Form | What it provides | Useful when |
|---|---|---|
| CTE | A named result within one statement | Several understandable steps, repeated references, or recursion |
| Subquery | A query nested inside another query | A short lookup, comparison, or intermediate result is easy to read in place |
| Temporary table | Stored rows in a temporary database object | Later statements must reuse or inspect an intermediate dataset |
| Ordinary view | A saved query definition that can be queried by name | Multiple queries need a shared definition; the definition persists until removed |

Temporary-table lifetime depends on the engine and context. A view stores a definition; an ordinary view is not a saved snapshot of the rows. A CTE definition does not create either of these objects. [SQLite table creation](https://www.sqlite.org/lang_createtable.html#the_create_table_command), [SQLite views](https://www.sqlite.org/lang_createview.html)

### The same department summary as a subquery

Using the earlier employee fixture:

```sql
SELECT
    d.department,
    ROUND(d.avg_salary, 2) AS avg_salary
FROM (
    SELECT department, AVG(1.0 * salary) AS avg_salary
    FROM employees
    GROUP BY department
) AS d
ORDER BY d.department;
```

The result is the same three rows as `avg_salary_by_dept`: Engineering `73333.33`, Management `120000`, and Sales `80000`. The subquery is placed inside `FROM`; the CTE gives that definition a name before the final query. This is a readability choice, not evidence that one runs faster.

### Reusing a CTE name within one statement

Find the department with the highest average using the same summary twice:

```sql
WITH avg_salary_by_dept AS (
    SELECT department, AVG(1.0 * salary) AS avg_salary
    FROM employees
    GROUP BY department
)
SELECT department, ROUND(avg_salary, 2) AS avg_salary
FROM avg_salary_by_dept
WHERE avg_salary = (
    SELECT MAX(avg_salary)
    FROM avg_salary_by_dept
)
ORDER BY department;
```

The outer query reads department rows; the scalar subquery reads the same named summary to find its maximum, `120000`. The result is Management, `120000`. If several departments share the maximum, this equality keeps them all. Reusing the definition does not guarantee that its calculation is cached.

## Dialect and performance notes

| Concern | SQLite | SQL Server |
|---|---|---|
| Ordinary CTE | `WITH name AS (...)` | Same structure; `;WITH` can terminate a preceding statement |
| Several definitions | One `WITH`, commas between CTEs | Same; define dependencies before their consumers |
| Recursive examples in this guide | `WITH RECURSIVE` | `WITH`, without `RECURSIVE` |
| Text full name | `first_name || ' ' || last_name` | `CONCAT(first_name, ' ', last_name)`; check NULL behavior |
| Decimal division | Use `1.0` or another decimal operand | Same principle |
| Output order | Put `ORDER BY` on the final query | Same; a bare `ORDER BY` inside a CTE is restricted |
| Recursion limit shown here | No `MAXRECURSION` option | Outer `OPTION (MAXRECURSION n)` |

CTEs can also precede data-changing statements. SQLite supports `WITH` before `INSERT`, `UPDATE`, and `DELETE`; SQL Server also supports `MERGE`. That does not mean every CTE can itself be an update target. This guide uses read-only final queries. [SQLite WITH](https://www.sqlite.org/lang_with.html), [SQL Server WITH](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql?view=sql-server-ver17)

**Choose CTEs for clarity; measure performance separately.** The optimizer decides how to execute a query. SQL Server does not promise a materialized, reusable CTE result. SQLite can choose how to implement it; its optional materialization hints are unnecessary for these foundation examples. Indexes, filters, join sizes, and the actual execution plan matter more than adding `WITH`. [SQL Server CTE usage guidelines](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql?view=sql-server-ver17#usage-guidelines), [SQLite optimizer overview](https://www.sqlite.org/optoverview.html#subquery_co_routines), [SQLite materialization hints](https://www.sqlite.org/lang_with.html#materialization_hints)

The diagrams and intermediate tables in these notes explain the **logical flow**. They do not promise that the engine creates and stores every displayed table in that order.

## Common mistakes and debugging

| Mistake | Why it fails or misleads | What to do |
|---|---|---|
| End the CTE definition with `;` before its consumer | Separates a definition from the statement using it | Put the terminator after the final query |
| Write a second `WITH` for the next ordinary CTE | Does not form the intended list of definitions | Separate definitions with commas |
| Refer to a column not selected by the CTE | That column is absent from the intermediate result | Select it there, or join the appropriate source |
| Expect the CTE name to work in the next statement | Its name has statement scope | Redefine it, or choose a suitable reusable object |
| Add `pid` or another unique row ID to every grouping | Can turn a required multirow group into one-row groups | Group by the identity of the intended summary |
| Use `WHERE COUNT(*) > 1` inside a grouped query | A row filter is not a group filter | Use `HAVING`; or expose the count in a CTE and filter it outside |
| Use `COUNT(*)` for missing matches after a left join | The preserved unmatched row is still a row | Count a non-NULL matched column when counting matches |
| Divide integer counts and multiply by 100 afterward | Fractional information may already be lost | Use `100.0 * numerator / denominator` |
| Round an average before a comparison | Rounding can change which near-boundary rows qualify | Compare the original value; round the displayed result |
| Cross join two multirow summaries accidentally | Combines every row on one side with every row on the other | Predict the multiplication; use a join key when matching groups |
| Assume recursion visits every row in the table | Only rows reachable from the chosen anchor are found | Check the anchor, relationship, and stopping condition |

To debug, keep the relevant `WITH` definitions and temporarily make the final consumer `SELECT * FROM the_step_you_want_to_check;`. Re-run the whole statement for each inspection. Check columns, row counts, and NULLs before adding the next operation.

For example, a grouped CTE exposing `confirmed_count` allows an outer `WHERE confirmed_count > 0`: the count is already a column of the intermediate result. This is different from trying to use an aggregate in the original row-level `WHERE`.

## Quick revision sheet

| Remember | Short explanation |
|---|---|
| CTE = Common Table Expression | Name an intermediate query result |
| Scope | One statement; no separate cleanup statement is needed |
| Shape | `WITH step AS (...) SELECT ... FROM step;` |
| Several steps | `WITH a AS (...), b AS (...) SELECT ...;` |
| Independent CTEs | Compute separate inputs, then combine them |
| Dependent CTEs | One step reads an earlier step |
| Recursive CTE | Anchor + recursive relationship + termination |
| Counts and sums | Their meaning depends on which rows enter the calculation |
| Reuse | A name can be referenced more than once; caching is not guaranteed |
| Best habit | State what one row means before writing each CTE |

When stuck, write these planning sentences before SQL:

1. **My final output has one row per ...**
2. **First, I need a table containing ...**
3. **Each row of that table means ...**
4. **Next, I will join/filter/group it using ...**
5. **On the sample, I expect ... rows and these values ...**

Then write one part and inspect its result. A useful CTE name describes the data it contains: `first_orders`, `contest_attendance`, or `confirmation_counts`. Add another CTE when it separates a meaningful stage, rather than putting every clause in its own block.
