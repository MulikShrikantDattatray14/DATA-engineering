# Windowing Functions - Quick Revision Notes

**Main idea:** calculate something across related rows while keeping each row visible.

Read in this order: **keep rows -> choose a partition -> choose an order -> choose a frame -> calculate -> filter**.

The examples reuse the sales and scores from your slides. They use SQLite and also work in SQL Server unless labelled otherwise. Run the optional setup at the end if you want to try them.

## 1. Window functions versus GROUP BY

Use this small `Sales` table throughout the sales examples. For these examples, `id` gives the sale sequence.

| id | customer | amount |
|---|---|---|
| 1 | A | 100 |
| 2 | B | 200 |
| 3 | A | 300 |
| 4 | B | 400 |
| 5 | A | 500 |

### GROUP BY: one result row per customer

```sql
SELECT customer, SUM(amount) AS customer_total
FROM Sales
GROUP BY customer
ORDER BY customer;
```

| customer | customer_total |
|---|---|
| A | 900 |
| B | 600 |

The five sales become two customer summaries.

### Window function: keep each sale and attach the customer total

```sql
SELECT id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS customer_total
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | customer_total |
|---|---|---|---|
| 1 | A | 100 | 900 |
| 3 | A | 300 | 900 |
| 5 | A | 500 | 900 |
| 2 | B | 200 | 600 |
| 4 | B | 400 | 600 |

For every A row, SQL calculates `100 + 300 + 500 = 900`. For every B row, it calculates `200 + 400 = 600`.

**Choose by the output:** one summary per customer -> `GROUP BY`; each sale plus a summary -> window function.

## 2. Read OVER in three parts

General shape; the bracketed parts are placeholders, not literal SQL:

```text
function(...) OVER (
    [PARTITION BY group_columns]
    [ORDER BY sequence_columns]
    [frame]
)
```

| Part | Question it answers | Sales example |
|---|---|---|
| Function | What do I calculate? | SUM(amount) |
| PARTITION BY | Which rows belong together? | One partition per customer |
| ORDER BY inside OVER | In what sequence? | Earlier sale id first |
| Frame | Which rows around this row contribute? | First sale through this sale |

A **partition** is the full group. A **frame** is the portion used for a particular row's calculation. They are not additional stored tables.

| Expression | Meaning |
|---|---|
| `SUM(amount) OVER ()` | Total of all five sales: 1500 on every row |
| `SUM(amount) OVER (PARTITION BY customer)` | Whole customer total: A = 900, B = 600 |
| `SUM(amount) OVER (ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` | Running total across all customers, in id order: 100, 300, 600, 1000, 1500 |
| `SUM(amount) OVER (PARTITION BY customer ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` | Customer's total so far |

Without `PARTITION BY`, all rows reaching the window calculation belong to one partition. Rows for the same partition need not sit next to each other in the original input. In the running-total forms above, `ORDER BY id` gives the sequence; adding `PARTITION BY customer` makes each customer's total restart separately.

**Two ORDER BY clauses have different jobs:** the one inside `OVER` controls the calculation; the final `ORDER BY` controls the displayed result. Keep the final one when the question requires a sorted answer. [OVER documentation](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-over-clause-transact-sql?view=sql-server-ver17)

## 3. Aggregate window functions

Use familiar aggregates with `OVER` to keep the detail rows.

```sql
SELECT id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS total_amount,
       AVG(1.0 * amount) OVER (PARTITION BY customer) AS avg_amount,
       COUNT(*) OVER (PARTITION BY customer) AS sale_count,
       MIN(amount) OVER (PARTITION BY customer) AS smallest,
       MAX(amount) OVER (PARTITION BY customer) AS largest
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | total_amount | avg_amount | sale_count | smallest | largest |
|---|---|---|---|---|---|---|---|
| 1 | A | 100 | 900 | 300 | 3 | 100 | 500 |
| 3 | A | 300 | 900 | 300 | 3 | 100 | 500 |
| 5 | A | 500 | 900 | 300 | 3 | 100 | 500 |
| 2 | B | 200 | 600 | 300 | 2 | 200 | 400 |
| 4 | B | 400 | 600 | 300 | 2 | 200 | 400 |

For A: average = `900 / 3 = 300`. No ordering is needed inside `OVER` when we want the whole partition's aggregate.

`COUNT(*)` counts rows; `COUNT(amount)` counts non-NULL amounts. `SUM`, `AVG`, `MIN`, and `MAX` ignore NULL inputs.

**Decimal habit:** `AVG(1.0 * amount)` preserves fractional averages in SQL Server, where `AVG` of an integer expression returns an integer. SQLite already returns a floating-point average. [SQL Server AVG](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql?view=sql-server-ver17)

## 4. Running totals and moving averages

### Running total: keep adding as you move forward

```sql
SELECT id, customer, amount,
       SUM(amount) OVER (
           PARTITION BY customer
           ORDER BY id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | running_total |
|---|---|---|---|
| 1 | A | 100 | 100 |
| 3 | A | 300 | 400 |
| 5 | A | 500 | 900 |
| 2 | B | 200 | 200 |
| 4 | B | 400 | 600 |

For A: `100 -> 100 + 300 -> 100 + 300 + 500`. The calculation restarts for B.

### Moving average: current sale and one previous sale

```sql
SELECT id, customer, amount,
       AVG(1.0 * amount) OVER (
           PARTITION BY customer
           ORDER BY id
           ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
       ) AS moving_avg
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | Amounts included | moving_avg |
|---|---|---|---|---|
| 1 | A | 100 | 100 | 100 |
| 3 | A | 300 | 100, 300 | 200 |
| 5 | A | 500 | 300, 500 | 400 |
| 2 | B | 200 | 200 | 200 |
| 4 | B | 400 | 200, 400 | 300 |

"Amounts included" is an explanatory column. At the first sale, only one row is available, so the average uses that one row.

### Frame words to remember

| Frame | Meaning |
|---|---|
| `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | First row through current row |
| `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` | Current row plus up to two earlier rows |
| `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` | Previous, current and next rows, where available |
| `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` | Whole partition, even with window ordering |

**ROWS counts rows, not days.** Seven daily totals represent seven days only when there is one row per day and no dates are missing. If several purchases occur on the same date, aggregate by date first. Decide whether an incomplete initial window should be included.

### ROWS versus the default RANGE: ties matter

For an aggregate with window `ORDER BY` and no explicit frame, SQLite and SQL Server use `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. This includes all rows tied with the current row on the window's ordering values. [SQLite frames](https://www.sqlite.org/windowfunctions.html#frame_specifications), [SQL Server frames](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-over-clause-transact-sql?view=sql-server-ver17)

Use the slide's `Scores` data, with `score_id` added as a unique tie-breaker:

| score_id | name | score |
|---|---|---|
| 1 | Bob | 95 |
| 2 | Charlie | 95 |
| 3 | Alice | 90 |
| 4 | David | 85 |
| 5 | Emma | 80 |

```sql
SELECT name, score,
       SUM(score) OVER (ORDER BY score DESC) AS default_total,
       SUM(score) OVER (
           ORDER BY score DESC, score_id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS row_total
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | default_total | row_total |
|---|---|---|---|
| Bob | 95 | 190 | 95 |
| Charlie | 95 | 190 | 190 |
| Alice | 90 | 280 | 280 |
| David | 85 | 365 | 365 |
| Emma | 80 | 445 | 445 |

Both 95s are included together in `default_total`. Explicit `ROWS` plus a unique order makes `row_total` advance one row at a time.

## 5. ROW_NUMBER, RANK and DENSE_RANK

Using the same five scores:

```sql
SELECT name, score,
       ROW_NUMBER() OVER (ORDER BY score DESC, score_id) AS row_num,
       RANK() OVER (ORDER BY score DESC) AS score_rank,
       DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rank
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | row_num | score_rank | dense_rank |
|---|---|---|---|---|
| Bob | 95 | 1 | 1 | 1 |
| Charlie | 95 | 2 | 1 | 1 |
| Alice | 90 | 3 | 3 | 2 |
| David | 85 | 4 | 4 | 3 |
| Emma | 80 | 5 | 5 | 4 |

| Function | Rule | Typical need |
|---|---|---|
| ROW_NUMBER() | A different number for each row | Choose exactly one row using a tie-breaker |
| RANK() | Ties share rank; later ranks have gaps | Competition positions |
| DENSE_RANK() | Ties share rank; no gaps | Second distinct value, top N distinct values |

**Why does only ROW_NUMBER include score_id?** It makes Bob/Charlie numbering predictable. Adding it to `RANK` or `DENSE_RANK` would make their ordering values different and remove the intended score tie.

To restart rankings for each customer, use a partition, for example:

```sql
SELECT customer, id, amount,
       DENSE_RANK() OVER (
           PARTITION BY customer ORDER BY amount DESC
       ) AS amount_rank
FROM Sales
ORDER BY customer, amount DESC, id;
```

A's amounts `500, 300, 100` receive ranks `1, 2, 3`. B's `400, 200` restart at `1, 2`.

## 6. Filter a window result using a CTE

In SQLite and SQL Server, calculate the window value first, then filter it in an outer query.

Example: keep everyone in the top **two distinct score levels**.

```sql
WITH ranked_scores AS (
    SELECT name, score,
           DENSE_RANK() OVER (ORDER BY score DESC) AS score_rank
    FROM Scores
)
SELECT name, score
FROM ranked_scores
WHERE score_rank <= 2
ORDER BY score DESC, name;
```

| name | score |
|---|---|
| Bob | 95 |
| Charlie | 95 |
| Alice | 90 |

The CTE produces all five ranked rows. The outer query keeps ranks 1 and 2, giving three people because the highest score is tied.

**Logical flow:** `FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> window calculations -> final ORDER BY`.

A window sees the rows remaining at its query level after earlier filtering/grouping. Do not place its expression or alias in that same query's `WHERE` or `HAVING`. If another calculation needs a window result, an additional CTE/query level also makes that dependency clear.

## 7. LAG and LEAD

- `LAG`: fetch a value from an earlier row in the partition's order.
- `LEAD`: fetch a value from a later row in that order.

```sql
SELECT id, customer, amount,
       LAG(amount) OVER (
           PARTITION BY customer ORDER BY id
       ) AS previous_amount,
       LEAD(amount) OVER (
           PARTITION BY customer ORDER BY id
       ) AS next_amount
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | previous_amount | next_amount |
|---|---|---|---|---|
| 1 | A | 100 | NULL | 300 |
| 3 | A | 300 | 100 | 500 |
| 5 | A | 500 | 300 | NULL |
| 2 | B | 200 | NULL | 400 |
| 4 | B | 400 | 200 | NULL |

For A's middle sale, the previous amount is 100 and the next is 500. Neither function crosses from A into B.

### Offset and default

```text
LAG(value, offset, default) OVER (...)
LEAD(value, offset, default) OVER (...)
```

| Expression, ordered by id within A | Results for amounts 100, 300, 500 |
|---|---|
| `LAG(amount)` | NULL, 100, 300 |
| `LAG(amount, 1, 0)` | 0, 100, 300 |
| `LAG(amount, 2, -1)` | -1, -1, 100 |
| `LEAD(amount, 2, -1)` | 500, -1, -1 |

The default offset is 1; the default missing-row result is NULL. The third argument applies when the requested row does not exist, not when an existing row contains NULL. [LAG arguments](https://learn.microsoft.com/en-us/sql/t-sql/functions/lag-transact-sql?view=sql-server-ver17)

A change from the previous sale is `amount - previous_amount`: for A, `NULL, 200, 200`.

**Previous row is not automatically previous day/month.** Order by a real date for chronological comparisons and check date gaps if required. Likewise, adjacent rows do not guarantee consecutive numeric IDs. For `LAG`/`LEAD`, choose the partition, order and offset; the aggregate frame recipes above do not define their offset.

## 8. NTILE and PERCENT_RANK

### NTILE: split ordered rows into buckets

Using the same five scores:

```sql
SELECT name, score,
       NTILE(2) OVER (ORDER BY score DESC, score_id) AS bucket
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | bucket |
|---|---|---|
| Bob | 95 | 1 |
| Charlie | 95 | 1 |
| Alice | 90 | 1 |
| David | 85 | 2 |
| Emma | 80 | 2 |

Five rows cannot split equally into two buckets, so sizes are **3 and 2**. Earlier buckets receive extra rows. With eight rows and `NTILE(4)`, sizes are `2, 2, 2, 2`; with nine rows, they are `3, 2, 2, 2`.

Buckets balance **row counts**, not value ranges. Equal scores can fall in different buckets. `ORDER BY score DESC` puts higher scores in earlier buckets. [NTILE rules](https://learn.microsoft.com/en-us/sql/t-sql/functions/ntile-transact-sql?view=sql-server-ver17)

### PERCENT_RANK: relative rank from 0 to 1

```sql
SELECT name, score,
       PERCENT_RANK() OVER (ORDER BY score DESC) AS relative_rank
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | RANK used | relative_rank |
|---|---|---|---|
| Bob | 95 | 1 | 0 |
| Charlie | 95 | 1 | 0 |
| Alice | 90 | 3 | 0.50 |
| David | 85 | 4 | 0.75 |
| Emma | 80 | 5 | 1.00 |

"RANK used" explains the formula; it is not an extra selected column.

For more than one row: `(RANK - 1) / (partition row count - 1)`.
For Alice: `(3 - 1) / (5 - 1) = 0.50`.

A one-row partition returns 0. Multiply by 100 if a percentage is required. With descending score order, the highest scores have relative rank 0; this is not a percentage of marks. [PERCENT_RANK definition](https://www.sqlite.org/windowfunctions.html#built_in_window_functions)

## 9. Quick revision and common mistakes

### Choose the operation

| Requirement | Starting point |
|---|---|
| Collapse rows into one summary per group | GROUP BY |
| Keep rows and show the group total/average | Aggregate OVER (PARTITION BY ...) |
| Total so far | SUM + ORDER BY + explicit running ROWS frame |
| Average of the current and preceding rows | AVG + bounded ROWS frame |
| Exactly one selected row per group | ROW_NUMBER with a complete tie-breaker |
| Top N distinct values, including ties | DENSE_RANK |
| Competition ranks with gaps | RANK |
| Previous/next row's value | LAG / LEAD |
| Roughly equal-sized buckets | NTILE |
| Relative rank | PERCENT_RANK |
| Filter by a calculated window value | CTE/subquery, then outer WHERE |

Before writing SQL, fill in: **"For each ___, ordered by ___, calculate ___ using ___ rows."**

Example: "For each customer, ordered by sale id, calculate the total amount using the first row through the current row."

### Five checks before submitting

1. **Rows:** am I keeping the correct detail level? A join that duplicates rows also changes window calculations.
2. **Partition:** does the calculation restart for the correct entity? Prefer its unique ID when names can repeat.
3. **Order and ties:** is the order complete where needed, and are intended ties preserved?
4. **Frame and boundaries:** whole group or running/moving subset? Rows or dates? Missing neighbour or incomplete window?
5. **Final output:** filter in the right query level and apply the required final ordering.

Do not attach a frame to every function: the aggregate examples use frames; ranking functions such as `RANK` do not need them, and SQL Server disallows frames on ranking functions.

### Small dialect reminders

| Need | SQLite | SQL Server |
|---|---|---|
| Core examples in this guide | Same window syntax | Same window syntax |
| Preserve fractional average of integers | AVG(1.0 * amount) | AVG(1.0 * amount) |
| Add six calendar days | DATE('2020-01-01', '+6 days') | DATEADD(day, 6, CAST('2020-01-01' AS date)) |
| Days between date-only values | JULIANDAY('2020-01-07') - JULIANDAY('2020-01-01') | DATEDIFF(day, '2020-01-01', '2020-01-07') |
| COUNT(DISTINCT value) OVER (...) | Not supported | Not supported |

The date examples return January 7 and 6 days respectively. In SQLite, adding `6` directly to a date string is not calendar arithmetic. Two-argument `DATEDIFF(later, earlier)` in the class handout is MySQL syntax. SQL Server `DATEDIFF(day,...)` counts day boundaries, so do not treat it as elapsed 24-hour periods for timestamps. [SQLite dates](https://www.sqlite.org/lang_datefunc.html), [SQL Server DATEDIFF](https://learn.microsoft.com/en-us/sql/t-sql/functions/datediff-transact-sql?view=sql-server-ver17)
