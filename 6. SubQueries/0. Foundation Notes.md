# Section 6 foundation notes: SQL subqueries

These notes combine the two supplied subquery handouts into a revision guide. Start with **what the inner query must return**, then decide how the outer query will use it. Practice examples use SQLite; SQL Server differences are labelled.

The learning sequence is: **one value -> a list of values -> a result table -> dependence on an outer row -> existence and missing matches -> practice patterns**. Each worked example keeps the same input rows through its steps. The illustrative employee and student datasets are separate examples, not changes to the saved question schemas.

## How to use this guide

Before coding, complete these sentences:

1. **The final result needs one row per ...**
2. **To decide that, I first need to know ...**
3. **That missing information is one value, a list, a table, or a yes/no existence check.**
4. **It is the same for every outer row, or it depends on this row's ...**
5. **I will compare, test membership, check existence, or join accordingly.**

Example: “Find employees above their department average.” The final row is an employee. The missing information is one average salary. It depends on that employee's department. That suggests a correlated scalar subquery, or an equivalent grouped result joined by department.

For a short revision, read the [quick revision sheet](#quick-revision-sheet). For a complete revision, predict each inner result and then trace which outer rows pass.

## Subquery foundations: identify the value the outer query needs

A **subquery** is a query placed inside another SQL statement. The contained query is the **inner query**; the query using its result is the **outer query**. For example, “employees earning more than the company average” needs two ideas: calculate an average, then compare each employee's salary with that value.

Think “what does the inner query return, and how will the outer query use it?” This is a way to understand the answer, not a promise that the database physically executes every inner query first or that nesting automatically improves speed.

### Classify shape separately from dependence

First ask **what shape comes back**:

| Shape | What the outer operation expects | Typical use |
|---|---|---|
| Scalar | One column, at most one row: one value or NULL | Compare a salary with an average; display one calculated column |
| Row / multiple columns | A tuple such as `(DepartmentID, Salary)` | Compare a combination of values where supported |
| Table / multiple rows | Zero or more rows, with one or more columns | Read a derived table; test membership using `IN` |

“Single row” does not automatically mean “single value”: one row can contain several columns. Ordinary scalar comparisons such as `Salary > (subquery)` require a scalar result. Membership against one column can use `IN`; a subquery in `FROM` may return many columns and rows.

Separately ask **whether it refers to an outer-query column**:

| Dependence | Meaning | Example |
|---|---|---|
| Non-correlated | Does not refer to an outer-query alias; can be run independently | Company-wide average salary |
| Correlated | Uses a column from an outer-query row | Average salary for that employee's department |

A subquery can therefore be both **scalar and correlated**, or both **multiple-row and non-correlated**. These are two classification questions, not four mutually exclusive types.

### WHERE: compare each row with one scalar result

Inspect the company average independently:

```sql
SELECT AVG(1.0 * e.Salary) AS CompanyAverage
FROM Employees AS e;
```

| CompanyAverage |
|---|
| 68333.33333333333 |

The total is `410000`, divided by six employees. Now use that single value in the outer row filter:

```sql
SELECT e.EmployeeID, e.Name, e.Salary
FROM Employees AS e
WHERE e.Salary > (
    SELECT AVG(1.0 * i.Salary)
    FROM Employees AS i
)
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | Salary |
|---|---|---|
| 1 | Asha | 90000 |
| 3 | Chen | 80000 |
| 5 | Evan | 90000 |

Read this as “keep each outer employee whose salary exceeds the inner average.” The inner query uses only alias `i`, so it is non-correlated even though both queries read `Employees`. Sharing a table name does not establish correlation.

`AVG(1.0 * Salary)` supplies decimal input. SQL Server's `AVG` over an integer expression returns an integer type, so this avoids losing the fractional average there. Compare the unrounded average and round only presentation values. [SQL Server AVG return types](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql?view=sql-server-ver17)

### Scalar result does not mean a single outer result row

For the highest-paid employees:

```sql
SELECT e.EmployeeID, e.Name, e.Salary
FROM Employees AS e
WHERE e.Salary = (
    SELECT MAX(i.Salary)
    FROM Employees AS i
)
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | Salary |
|---|---|---|
| 1 | Asha | 90000 |
| 5 | Evan | 90000 |

The inner maximum is one value, `90000`. Two outer rows match it, so both appear. An aggregate without `GROUP BY` is useful when one summary value is required; adding `GROUP BY DepartmentID` would produce three averages instead of one.

A scalar subquery returning no rows evaluates to NULL. If it unexpectedly returns several rows, SQL Server raises an error, whereas SQLite uses the first row. Do not rely on SQLite silently choosing a row; make the query's intended cardinality clear. Adding an arbitrary `LIMIT 1` can hide a logic error. [SQLite scalar subqueries](https://www.sqlite.org/lang_expr.html#subquery_expressions), [SQL Server single-value subqueries](https://learn.microsoft.com/en-us/sql/relational-databases/performance/subqueries?view=sql-server-ver17#subqueries-with-comparison-operators)

### WHERE with IN: compare against a one-column collection

Find the eligible department IDs first:

```sql
SELECT d.DepartmentID
FROM Departments AS d
WHERE d.Location = 'New York'
ORDER BY d.DepartmentID;
```

Result: `10`, `30`. The outer query needs membership in either department:

```sql
SELECT e.EmployeeID, e.Name, e.DepartmentID
FROM Employees AS e
WHERE e.DepartmentID IN (
    SELECT d.DepartmentID
    FROM Departments AS d
    WHERE d.Location = 'New York'
)
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | DepartmentID |
|---|---|---|
| 1 | Asha | 10 |
| 2 | Ben | 10 |
| 5 | Evan | 30 |
| 6 | Farah | 30 |

The compared values represent the same thing: department IDs on both sides. Comparing `EmployeeID` to this collection would test the wrong relationship. The inner query remains non-correlated because it does not use `e`.

### FROM: turn a summary into an input table

A subquery in `FROM` is a **derived table**. Its alias names the rows and columns available to the outer query; it does not create a stored table.

```sql
SELECT summary.DepartmentID, summary.DepartmentAverage
FROM (
    SELECT e.DepartmentID,
           AVG(1.0 * e.Salary) AS DepartmentAverage
    FROM Employees AS e
    GROUP BY e.DepartmentID
) AS summary
ORDER BY summary.DepartmentID;
```

| DepartmentID | DepartmentAverage |
|---|---|
| 10 | 75000 |
| 20 | 60000 |
| 30 | 70000 |

Six employee rows become three department summaries. HR is absent because the inner query reads employees, and there are no employee rows for department 40. The outer query sees only the two projected columns, not individual employee names.

Keep `AS summary` for clear, portable references; SQL Server requires a derived-table alias. A derived table may also be an input to a join, using its exposed columns as join keys. [SQL Server FROM derived tables](https://learn.microsoft.com/en-us/sql/t-sql/queries/from-transact-sql?view=sql-server-ver17#derived-table)

### HAVING: compare each group with a scalar benchmark

Find departments whose average salary exceeds the company average:

```sql
SELECT e.DepartmentID,
       AVG(1.0 * e.Salary) AS DepartmentAverage
FROM Employees AS e
GROUP BY e.DepartmentID
HAVING AVG(1.0 * e.Salary) > (
    SELECT AVG(1.0 * i.Salary)
    FROM Employees AS i
)
ORDER BY e.DepartmentID;
```

| DepartmentID | DepartmentAverage |
|---|---|
| 10 | 75000 |
| 30 | 70000 |

The inner scalar benchmark is still `68333.333...`. The outer grouping produces the three averages above; `HAVING` keeps `75000` and `70000`. `WHERE` filters individual employee rows before grouping; `HAVING` filters the department groups. Filtering employees first could change the averages and answer a different question.

### Correlation: the benchmark depends on the current employee

Change the question to “employees earning more than their **own department's** average”:

```sql
SELECT e.EmployeeID, e.Name, e.Salary, e.DepartmentID
FROM Employees AS e
WHERE e.Salary > (
    SELECT AVG(1.0 * i.Salary)
    FROM Employees AS i
    WHERE i.DepartmentID = e.DepartmentID
)
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | Salary | DepartmentID |
|---|---|---|---|
| 1 | Asha | 90000 | 10 |
| 3 | Chen | 80000 | 20 |
| 5 | Evan | 90000 | 30 |

`e` identifies the outer employee; `i` identifies employees considered inside the average. For Asha, the condition becomes `i.DepartmentID = 10`, averaging Asha and Ben to `75000`. For Chen, it uses department 20 and averages Chen and Diya to `60000`. For Evan, it uses department 30 and averages Evan and Farah to `70000`.

This fixture happens to return the same names as the global-average query. The logic differs: the global threshold is identical for everyone; the correlated threshold changes with the employee's department. Qualifying both sides prevents mistakenly writing `i.DepartmentID = i.DepartmentID`, which does not connect to the outer employee.

Think of substituting each outer department into the inner condition to understand the result. It is not a claim that the engine must physically rerun an identical scan per row or that correlation is always slower. [SQL Server correlated subqueries](https://learn.microsoft.com/en-us/sql/relational-databases/performance/subqueries?view=sql-server-ver17#correlated-subqueries)

### SELECT: display the scalar value beside each outer row

The same correlated scalar can become an output column instead of a filter:

```sql
SELECT
    e.EmployeeID,
    e.Name,
    e.Salary,
    (
        SELECT AVG(1.0 * i.Salary)
        FROM Employees AS i
        WHERE i.DepartmentID = e.DepartmentID
    ) AS DepartmentAverage
FROM Employees AS e
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | Salary | DepartmentAverage |
|---|---|---|---|
| 1 | Asha | 90000 | 75000 |
| 2 | Ben | 60000 | 75000 |
| 3 | Chen | 80000 | 60000 |
| 4 | Diya | 40000 | 60000 |
| 5 | Evan | 90000 | 70000 |
| 6 | Farah | 50000 | 70000 |

All six employees remain because there is no filtering predicate. Each scalar result fills one cell. This is also a useful debugging step: display the comparison value before deciding whether to filter a row.

### Multiple-column rows: one final shape distinction

SQLite can compare a pair against a two-column subquery:

```sql
-- SQLite row-value comparison
SELECT e.EmployeeID, e.Name
FROM Employees AS e
WHERE (e.DepartmentID, e.Salary) = (
    SELECT i.DepartmentID, i.Salary
    FROM Employees AS i
    WHERE i.EmployeeID = 1
)
ORDER BY e.EmployeeID;
```

The inner query returns one row containing `(10, 90000)`; the output is `(1, Asha)`. It is a **row result**, not a scalar. Column order matters, and both sides must have the same number of values. This tuple-comparison syntax is supported by SQLite; do not copy it unchanged into SQL Server. A join or correlated `EXISTS` can express the two comparisons there. [SQLite row values](https://www.sqlite.org/rowvalue.html)

## Membership and existence: IN, NOT IN, EXISTS, NOT EXISTS

Choose the question you need SQL to answer:

| Operator | Plain-English question |
| --- | --- |
| `IN` | Does this value match a value returned by the subquery? |
| `NOT IN` | Can SQL establish that this value matches none of those values? |
| `EXISTS` | Does the subquery return at least one row? |
| `NOT EXISTS` | Does the subquery return no rows? |

For a single-value `IN` test, the subquery returns one column and may return many rows. It does not need `DISTINCT`: repeated copies do not change membership. A multirow subquery does **not** always require `IN`, `ANY`, or `ALL`; it can also supply rows to `EXISTS` or act as a derived table in `FROM`. [SQL Server subquery forms](https://learn.microsoft.com/en-us/sql/relational-databases/performance/subqueries?view=sql-server-ver17)

### One small fixture makes the NULL behavior visible

Use `ProbeValues(value)` containing **10, 20, NULL**. Test candidates **10, 30, NULL** against that same set.

<details>
<summary>Runnable fixture setup for the following SQLite examples</summary>

```sql
CREATE TABLE ProbeValues (value INTEGER);
INSERT INTO ProbeValues (value) VALUES (10), (20), (NULL);

CREATE TABLE ProbeInputs (candidate INTEGER);
INSERT INTO ProbeInputs (candidate) VALUES (10), (30), (NULL);
```

</details>

```sql
-- SQLite: Boolean expressions can be selected directly.
SELECT
    p.candidate,
    p.candidate IN (SELECT v.value FROM ProbeValues AS v) AS in_result,
    p.candidate NOT IN (SELECT v.value FROM ProbeValues AS v) AS not_in_result
FROM ProbeInputs AS p
ORDER BY CASE WHEN p.candidate IS NULL THEN 1 ELSE 0 END,
         p.candidate;
```

| candidate | in_result | not_in_result |
| --- | --- | --- |
| 10 | 1 | 0 |
| 30 | NULL | NULL |
| NULL | NULL | NULL |

SQLite displays true as `1`, false as `0`, and unknown as `NULL`. In SQL Server, use these predicates in `WHERE` or `CASE`; do not copy the direct Boolean projection above unchanged.

For 10, a definite match settles `IN` as true despite the NULL elsewhere. For 30, neither 10 nor 20 matches, but comparison with an unknown value cannot establish a definite nonmatch. Therefore both `IN` and `NOT IN` are unknown. Negating unknown does not make it true. `WHERE` retains only true rows, so unknown results are filtered out. [SQL Server IN and NULL](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/in-transact-sql?view=sql-server-ver17), [NULL and three-valued logic](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/null-and-unknown-transact-sql?view=sql-server-ver17)

### When NOT IN is appropriate

If the compared values are guaranteed non-NULL, `NOT IN` clearly expresses nonmembership. Otherwise, excluding inner NULLs can be appropriate **when that matches the requirement**:

```sql
SELECT p.candidate
FROM ProbeInputs AS p
WHERE p.candidate IS NOT NULL
  AND p.candidate NOT IN (
      SELECT v.value
      FROM ProbeValues AS v
      WHERE v.value IS NOT NULL
  );
```

Output: one row, `30`. The inner filter removes unknown list entries; the outer filter explicitly excludes unknown candidates. These are separate decisions. Do not remove NULLs automatically without deciding what they mean.

An empty result set differs from a set containing NULL. In SQLite:

```sql
SELECT
    30 IN (SELECT value FROM ProbeValues WHERE 1 = 0) AS in_empty,
    NULL NOT IN (SELECT value FROM ProbeValues WHERE 1 = 0) AS not_in_empty;
```

Output: `in_empty = 0`, `not_in_empty = 1`. No value matches an empty set, even when the candidate is NULL. SQLite also accepts literal `IN ()`; SQL Server does not accept that empty-list syntax. An empty **subquery result** is valid. Prefer explicit business rules for outer NULLs over depending on whether the inner set happens to be empty. [SQLite membership and empty sets](https://www.sqlite.org/lang_expr.html#the_in_and_not_in_operators), [SQL Server IN syntax](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/in-transact-sql?view=sql-server-ver17#syntax)

### EXISTS tests rows, not the selected value

```sql
-- SQLite
SELECT
    EXISTS (SELECT NULL) AS has_row,
    EXISTS (SELECT 1 FROM ProbeValues WHERE value = 30) AS has_match,
    NOT EXISTS (SELECT 1 FROM ProbeValues WHERE value = 30) AS has_no_match;
```

| has_row | has_match | has_no_match |
| --- | --- | --- |
| 1 | 0 | 1 |

`SELECT NULL` still returns one row. `SELECT 1` is a conventional placeholder: it does not count rows or limit the subquery to one row. What matters is whether the subquery produces any rows. [SQL Server EXISTS](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/exists-transact-sql?view=sql-server-ver17)

Place the match condition in the inner `WHERE`:

```sql
SELECT p.candidate
FROM ProbeInputs AS p
WHERE NOT EXISTS (
    SELECT 1
    FROM ProbeValues AS v
    WHERE v.value = p.candidate
)
ORDER BY CASE WHEN p.candidate IS NULL THEN 1 ELSE 0 END,
         p.candidate;
```

Output: `30`, then `NULL`. Candidate 30 has no equality match. Candidate NULL also has no equality match: `NULL = NULL` is unknown, so the inner `WHERE` retains no row. `NOT EXISTS` therefore includes it. Add `p.candidate IS NOT NULL AND` before `NOT EXISTS` if unknown candidates must be excluded; that version returns only 30.

For **Students With Invalid Departments**, compare `d.id = s.department_id`, not `d.id = s.id`. A `NOT EXISTS` version includes an outer NULL department unless you add `s.department_id IS NOT NULL`. For **Employees Whose Manager Left**, explicitly requiring `manager_id IS NOT NULL` distinguishes a missing former manager from having no manager. The matching rule and the NULL policy together define the answer.

Two common traps:

- `EXISTS (SELECT CASE ... FROM ...)` tests whether rows exist; values such as 0 or NULL in those rows do not make it false. Move the required condition into `WHERE`.
- `EXISTS (SELECT COUNT(*) FROM ... WHERE ...)` is true even when the count is 0: an ungrouped aggregate returns a row. Use `EXISTS (SELECT 1 FROM ... WHERE ...)` to test for matching rows.

## ANY and ALL: comparisons across a set in SQL Server

SQL Server supports `ANY` (also called `SOME`) and `ALL`; SQLite does not support this quantified-comparison syntax. Consider salaries **40, 60, 90**:

```sql
-- SQL Server; standalone example
SELECT
    CASE WHEN 70 > ANY (
        SELECT salary FROM (VALUES (40), (60), (90)) AS v(salary)
    ) THEN 1 ELSE 0 END AS greater_than_any,
    CASE WHEN 70 > ALL (
        SELECT salary FROM (VALUES (40), (60), (90)) AS v(salary)
    ) THEN 1 ELSE 0 END AS greater_than_all;
```

| greater_than_any | greater_than_all |
| --- | --- |
| 1 | 0 |

`> ANY` needs at least one successful comparison: 70 exceeds 40 and 60. `> ALL` needs every comparison to succeed, but 70 does not exceed 90. [SQL Server ANY/SOME](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/some-any-transact-sql?view=sql-server-ver17), [SQL Server ALL](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/all-transact-sql?view=sql-server-ver17)

For a **nonempty set with no NULLs**, `> ANY` has the same result as comparison with `MIN`, and `> ALL` as comparison with `MAX`. Do not use those shortcuts blindly:

| Set compared with 70 | `70 > ANY` | `70 > ALL` |
| --- | --- | --- |
| 40, NULL | True | Unknown |
| 90, NULL | Unknown | False |
| Empty set | False | True |

A definite true settles `ANY`; a definite false settles `ALL`. Otherwise, a NULL comparison can leave the result unknown. Empty sets have no successful comparison for `ANY` and no violating comparison for `ALL`. In contrast, `MIN`/`MAX` ignore NULLs and return NULL for empty input, so those rewrites can change the answer. Also, `CASE WHEN predicate THEN 1 ELSE 0 END` combines false and unknown into 0; use an explicit unknown branch if that distinction matters. [SQL Server comparison rules](https://learn.microsoft.com/en-us/sql/relational-databases/performance/subqueries?view=sql-server-ver17#comparison-operators-modified-by-any-some-or-all)

The SQLite examples above were executed against the displayed fixture. The SQL Server `ANY`/`ALL` example and rules were checked against official documentation; no SQL Server execution is claimed.

### WHERE IN: keep rows whose key belongs to a result

Start with the requirement: return student details for Section A. The inner query produces roll numbers 101, 103 and 201. The outer query checks membership; it gets the name, location and phone number from Student_Info.

```sql
SELECT NAME, LOCATION, PHONE_NUMBER
FROM Student_Info
WHERE ROLL_NO IN (
    SELECT ROLL_NO
    FROM Student_Section
    WHERE SECTION = 'A'
)
ORDER BY ROLL_NO;
```

| NAME | LOCATION | PHONE_NUMBER |
|---|---|---|
| Sophia | London | 111-0101 |
| Maya | Berlin | 111-0103 |
| Noah | Toronto | 111-0201 |

IN accepts multiple rows but expects one column here. It checks membership without adding section columns or multiplying rows for duplicate matches. Existing duplicate Student_Info rows still remain.

### FROM: expose a derived table's columns

Now the requirement is names and phone numbers for locations beginning with T. The inner query keeps Liam in Tokyo and Noah in Toronto, exposing NAME, PHONE_NUMBER and LOCATION. The outer query selects two of those columns.

```sql
SELECT NAME, PHONE_NUMBER
FROM (
    SELECT NAME, PHONE_NUMBER, LOCATION
    FROM Student_Info
    WHERE LOCATION LIKE 'T%'
) AS subquery_table
ORDER BY NAME;
```

| NAME | PHONE_NUMBER |
|---|---|
| Liam | 111-0102 |
| Noah | 111-0201 |

The alias subquery_table names a statement-local result, not a stored table. The outer query cannot request ROLL_NO because the inner SELECT did not expose it. This simple filter could also be written without nesting; it demonstrates FROM subquery syntax.

### JOIN: attach matching columns and consider row counts

To include SECTION in the result, join to a derived table that exposes both the matching key and the section value.

```sql
SELECT s.NAME, s.LOCATION, ns.SECTION
FROM Student_Info AS s
JOIN (
    SELECT ROLL_NO, SECTION
    FROM Student_Section
    WHERE SECTION = 'A'
) AS ns ON s.ROLL_NO = ns.ROLL_NO
ORDER BY s.ROLL_NO;
```

| NAME | LOCATION | SECTION |
|---|---|---|
| Sophia | London | A |
| Maya | Berlin | A |
| Noah | Toronto | A |

Each matching pair becomes a result row. Adding another (101, A) would make this JOIN return Sophia twice: four rows versus three for IN. Choose membership for existence checks; use a join for matching-row details while accounting for multiplicity.

### UPDATE: preview the target rows, then change a value

This and the DELETE example **each start independently from the original fixture**, in a throwaway practice database. The chapter's validation used separate in-memory databases; it did not change any user database.

The article changes names to Geeks for locations returned by its subquery. Preview the same condition first:

```sql
SELECT ROLL_NO, NAME, LOCATION
FROM Student_Info
WHERE LOCATION IN (
    SELECT LOCATION FROM Student_Info
    WHERE LOCATION IN ('London', 'Berlin')
)
ORDER BY ROLL_NO;
```

| ROLL_NO | NAME | LOCATION |
|---|---|---|
| 101 | Sophia | London |
| 103 | Maya | Berlin |

Then run the modification and inspect the affected rows:

```sql
UPDATE Student_Info
SET NAME = 'Geeks'
WHERE LOCATION IN (
    SELECT LOCATION FROM Student_Info

SELECT ROLL_NO, NAME, LOCATION
FROM Student_Info
```

| ROLL_NO | NAME | LOCATION |
|---|---|---|
| 101 | Geeks | London |
| 103 | Geeks | Berlin |

Only NAME changes. SQLite permits this subquery to read the UPDATE target table. A direct location filter also works here; nesting illustrates a modification subquery.

### DELETE: preview the selected keys, then inspect survivors

Use a fresh copy of the original five rows. The condition selects roll numbers at most 101, plus 201. The preview returns Sophia and Noah:

```sql
SELECT ROLL_NO, NAME
FROM Student_Info
WHERE ROLL_NO IN (
    SELECT ROLL_NO FROM Student_Info
    WHERE ROLL_NO <= 101 OR ROLL_NO = 201
)
ORDER BY ROLL_NO;
```

| ROLL_NO | NAME |
|---|---|
| 101 | Sophia |
| 201 | Noah |

Delete those Student_Info rows and inspect what remains:

```sql
DELETE FROM Student_Info
WHERE ROLL_NO IN (
    SELECT ROLL_NO FROM Student_Info
    WHERE ROLL_NO <= 101 OR ROLL_NO = 201
);
SELECT ROLL_NO, NAME, LOCATION, PHONE_NUMBER
FROM Student_Info
ORDER BY ROLL_NO;
```

| ROLL_NO | NAME | LOCATION | PHONE_NUMBER |
|---|---|---|---|
| 102 | Liam | Tokyo | 111-0102 |
| 103 | Maya | Berlin | 111-0103 |
| 202 | Ava | Sydney | 111-0202 |

The article wraps the inner SELECT in another derived table named temp. SQLite does not need that extra layer; it is not a universal requirement. Only Student_Info changes: Student_Section remains untouched, with no cascading relationship defined.

Identify the inner result: a membership list, a derived table, or keys to modify. Then inspect the outer operation. All displayed outputs were checked using SQLite.

### 1. Invalid departments: compare the relationship column

In [Students With Invalid Departments](<1.Sql Students With Invalid Departments.md>), the inner query returns existing department IDs: `1, 7, 13`.

```sql
SELECT s.id, s.name
FROM Students AS s
WHERE s.department_id NOT IN (
    SELECT d.id
    FROM Departments AS d
)
ORDER BY s.id;
```

| Student | department_id being tested | In the existing departments? |
|---|---|---|
| Alice | 1 | Yes |
| John | 14 | No |
| Steve | 74 | No |
| Jasmine | 77 | No |
| Daiana | 33 | No |

The final rows are `(2, John), (3, Steve), (4, Jasmine), (7, Daiana)`. The remaining supplied students all reference valid departments.

The comparison is **student.department_id against department.id**, not student.id against department.id. In this problem, the referenced department IDs are non-NULL keys, so the inner list does not contain the NULL trap discussed earlier. Decide separately what a NULL `department_id` should mean in a different problem.

The classroom handout permits any order. The saved repository question explicitly asks for ascending student ID, so that order is used here.

### 2. A manager left: keep the full lookup population

In [Employees Whose Manager Has Left](<2.Sql Employees Who Manager Has Left The Company.md>), the current employee IDs are `1, 3, 9, 11, 12, 13`.

The salary condition leaves two candidates:

| employee_id | name | salary | manager_id | Manager still present? |
|---|---|---|---|---|
| 1 | Kalel | 21241 | 11 | Yes |
| 11 | Joziah | 28485 | 6 | No |

```sql
SELECT e.employee_id
FROM Employees AS e
WHERE e.salary < 30000
  AND e.manager_id NOT IN (
      SELECT current_employee.employee_id
      FROM Employees AS current_employee
  )
ORDER BY e.employee_id;
```

Output: employee `11`.

The outer salary filter concerns the employee being reported. The inner query must search **all current employees**, including highly paid managers. Adding `salary < 30000` inside it would incorrectly treat a manager above that salary as absent.

A NULL `manager_id` means no assigned manager. With the nonempty, non-NULL employee-ID list in this query, it does not pass `NOT IN`; it is not evidence that someone left.

### 3. Exchange seats: use a scalar result inside CASE

In [Exchange Seats](<3.Sql Exchange Seats.md>), the subquery `SELECT MAX(id) FROM Seat` returns one value: `5`. Reuse that value to decide whether an odd seat has a next partner.

| Original id | student | Calculated new id |
|---|---|---|
| 1 | Abbot | 2 |
| 2 | Doris | 1 |
| 3 | Emerson | 4 |
| 4 | Green | 3 |
| 5 | Jeames | 5 |

Your saved approach calculates the new ID:

```sql
SELECT
    CASE
        WHEN id % 2 = 0 THEN id - 1
        WHEN id % 2 = 1 AND (SELECT MAX(id) FROM Seat) > id
            THEN id + 1
        ELSE id
    END AS id,
    student
FROM Seat
ORDER BY id;
```

The result ordered by new ID is Doris, Abbot, Green, Emerson, Jeames in seats 1–5. Every student remains; a `WHERE` filter for the last seat would remove students who still need to appear.

This relies on the stated consecutive IDs starting at 1. The handout instead keeps each output ID and looks up its partner's student name with a correlated scalar subquery. Both express the swap; your saved query remains the version above.

### 4. Movie ratings: select one winner in each subquery

Using the [Movie Ratings](<4.Sql Movie Ratings.md>) sample, the two summaries are:

| User, across all dates | Movies rated |
|---|---|
| Daniel | 3 |
| Monica | 3 |
| Maria | 2 |
| James | 1 |

| Movie | February ratings | Average |
|---|---|---|
| Frozen 2 | 5, 2 | 3.5 |
| Joker | 3, 4 | 3.5 |
| Avengers | 4, 2 | 3.0 |

Sort each summary by its measure descending and its name ascending. Daniel and Frozen 2 win their respective ties.

The following is an **illustrative adaptation of the handout's scalar-lookup approach**. Each inner query returns the ID of one winner; the containing query retrieves that ID's name. A final wrapper orders the two result categories explicitly:

```sql
SELECT winners.results
FROM (
    SELECT 1 AS result_order, u.name AS results
    FROM Users AS u
    WHERE u.user_id = (
        SELECT r.user_id
        FROM MovieRating AS r
        JOIN Users AS names ON names.user_id = r.user_id
        GROUP BY r.user_id, names.name
        ORDER BY COUNT(*) DESC, names.name ASC
        LIMIT 1
    )

    UNION ALL

    SELECT 2 AS result_order, m.title AS results
    FROM Movies AS m
    WHERE m.movie_id = (
        SELECT r.movie_id
        FROM MovieRating AS r
        JOIN Movies AS titles ON titles.movie_id = r.movie_id
        WHERE r.created_at >= '2020-02-01'
          AND r.created_at < '2020-03-01'
        GROUP BY r.movie_id, titles.title
        ORDER BY AVG(1.0 * r.rating) DESC, titles.title ASC
        LIMIT 1
    )
) AS winners
ORDER BY winners.result_order;
```

| results |
|---|
| Daniel |
| Frozen 2 |

Each `LIMIT 1` belongs to its own ordered subquery. The date filter belongs only to the movie calculation. The February interval includes the first day and excludes March 1, including when timestamps are present.

`UNION ALL` preserves both category rows if a user and a movie happen to share a name. The final `ORDER BY` controls their displayed sequence; the order of written union branches is not a general output-order guarantee.

Your saved solution uses two derived tables instead. This example illustrates another subquery placement without replacing that solution.

### 5. Most friends: let a derived table collect both roles

The [Friend Requests](<5.Sql Friend Requests Ii Who Has The Most Friends.md>) sample contains accepted pairs `(1,2), (1,3), (2,3), (3,4)`. Every pair contributes once to each person's count.

The handout stacks the raw IDs:

| Branch | IDs produced, with repeats |
|---|---|
| requester_id | 1, 1, 2, 3 |
| accepter_id | 2, 3, 3, 4 |

```sql
SELECT id, COUNT(*) AS num
FROM (
    SELECT requester_id AS id
    FROM RequestAccepted
    UNION ALL
    SELECT accepter_id AS id
    FROM RequestAccepted
) AS all_friends
GROUP BY id
ORDER BY num DESC
LIMIT 1;
```

The grouped counts are `1 -> 2`, `2 -> 2`, `3 -> 3`, and `4 -> 1`. The final row is `id = 3, num = 3`. The question guarantees one winner.

`all_friends` is a **table result**, so its eight rows are valid inside `FROM`. `UNION` would remove repeated IDs and destroy the counts. Your saved alternative first groups each role, then stacks and sums those counts; both approaches count the two sides of each accepted friendship.

## Compare a pair of columns together

A multi-column subquery is useful when two values identify one thing. In [Investments In 2016](<6.Sql Investments In 2016.md>), the city is the **pair `(lat, lon)`**. This is the section's sixth existing problem; it was not included in the new handout.

The saved sample has these city counts:

| lat | lon | Number of policies |
|---|---|---|
| 10 | 10 | 1 |
| 20 | 20 | 2 |
| 40 | 40 | 1 |

SQLite can test membership in the two-column result directly:

```sql
SELECT i.pid, i.lat, i.lon
FROM Insurance AS i
WHERE (i.lat, i.lon) IN (
    SELECT city.lat, city.lon
    FROM Insurance AS city
    GROUP BY city.lat, city.lon
    HAVING COUNT(*) = 1
)
ORDER BY i.pid;
```

This returns policies 1 at `(10,10)` and 4 at `(40,40)`. It demonstrates only the city condition; the complete problem also requires a repeated `tiv_2015`.

Do not split a pair into independent latitude and longitude membership tests. For example, allowed pairs `(10,20)` and `(30,40)` do **not** allow `(10,40)`, even though each individual number appears in the appropriate column. Matching values must come from the same row. [SQLite row-value IN](https://www.sqlite.org/rowvalue.html#row_value_in_operators)

SQL Server does not use this tuple-IN form. The equivalent city filter can use a correlated `EXISTS`:

```sql
SELECT i.pid, i.lat, i.lon
FROM Insurance AS i
WHERE EXISTS (
    SELECT 1
    FROM Insurance AS city
    WHERE city.lat = i.lat
      AND city.lon = i.lon
    GROUP BY city.lat, city.lon
    HAVING COUNT(*) = 1
)
ORDER BY i.pid;
```

Both coordinates are guaranteed non-NULL in this problem. Both forms inspect city uniqueness across the complete Insurance table, so policy 3 still shares a city with policy 2 even if policy 2 fails the separate investment test.

## Subquery, CTE, or join

Use the employee fixture from the core examples. The department averages are `75000`, `60000`, and `70000`; employees above their respective averages are Asha, Chen, and Evan.

The correlated subquery shown earlier can also be expressed by naming those averages and joining them:

```sql
WITH department_averages AS (
    SELECT DepartmentID, AVG(1.0 * Salary) AS average_salary
    FROM Employees
    GROUP BY DepartmentID
)
SELECT e.EmployeeID, e.Name, e.Salary
FROM Employees AS e
JOIN department_averages AS d
    ON d.DepartmentID = e.DepartmentID
WHERE e.Salary > d.average_salary
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | Salary |
|---|---|---|
| 1 | Asha | 90000 |
| 3 | Chen | 80000 |
| 5 | Evan | 90000 |

Each employee matches one department summary, so the join does not multiply employee rows. The calculation is the same; the CTE makes the intermediate table explicit.

| Need | Useful starting point |
|---|---|
| Compare a value with a maximum or average | Scalar subquery |
| Keep rows whose key belongs to a lookup result | `IN` |
| Check whether a related row exists | Correlated `EXISTS` |
| Find rows with no related match | `NOT EXISTS`, with an explicit rule for outer NULLs |
| Read several columns from matching rows | Join, after checking match counts |
| Give several stages descriptive names | CTE |

Rewriting a query does not prove it will be faster. Engines may transform equivalent forms into similar plans. Repeated correlated work can be expensive, but indexes, data sizes, filters, and the chosen execution plan determine the actual cost. [SQL Server subquery fundamentals](https://learn.microsoft.com/en-us/sql/relational-databases/performance/subqueries?view=sql-server-ver17#subquery-fundamentals)

Use [Section 5's CTE foundation notes](<../5. CTEs/0. Foundation Notes.md>) to revise named intermediate results.

## SQLite and SQL Server revision table

| Feature | SQLite practice | SQL Server |
|---|---|---|
| Scalar result with no rows | NULL | NULL |
| Scalar result with several rows | Uses its first result row; without ordering, do not rely on which one | Error; design for at most one row |
| Select one ordered winner | `ORDER BY ... LIMIT 1` | `SELECT TOP (1) ... ORDER BY ...` |
| Derived-table name | Use `AS meaningful_name` consistently | Alias required |
| Multiple-column membership | `(a, b) IN (SELECT a, b ...)` supported | Use a matching `EXISTS` or join |
| Quantified comparisons | `ANY` / `ALL` comparison syntax is not supported | Supported; account for NULLs and empty results |
| Join syntax used in the handout | `JOIN ... USING(column)` can work | Use `JOIN ... ON left.column = right.column` |
| Text and dates | Use single-quoted literals | Use single-quoted literals |
| Decimal average/division | Use `AVG(1.0 * value)` or decimal arithmetic when appropriate | Avoid integer `AVG`/division when fractions are needed |
| Grouping selected names | SQLite permits some bare-column cases | Include selected nonaggregate columns in `GROUP BY` |

Do not add `LIMIT 1` merely to hide an unexpected multirow result. Use it when the requirement asks for one winner, and specify the complete ranking and tie-break. A unique-key lookup or a scalar aggregate may already establish the required cardinality. [SQL Server TOP](https://learn.microsoft.com/en-us/sql/t-sql/queries/top-transact-sql?view=sql-server-ver17)

## Common mistakes and debugging

| Mistake | Why it is wrong | Better check |
|---|---|---|
| Compare student `id` with department `id` | The values identify different entities | Follow the relationship through `department_id` |
| Use `= (subquery)` when several values are expected | A scalar comparison needs one value | Decide whether the requirement means membership, existence, or a chosen single row |
| Select two columns for a scalar expression | One expression cannot hold a two-column table | Select the needed scalar, or use a table/row-valued form |
| Assume `NOT IN` and `NOT EXISTS` always agree | Inner and outer NULLs can change their behavior | Check both sides' NULL rules |
| Forget the correlation condition | A per-department average becomes a global average | Identify the inner-to-outer key comparison |
| Write `DepartmentID = DepartmentID` | Both may resolve to the same inner column | Qualify both sides: `inner_employee.DepartmentID = e.DepartmentID` |
| Reference an inner table alias outside its scope | The outer query cannot directly see that alias | Expose required columns through a derived table or join |
| Filter the lookup table using an outer-only condition | Changes the population used for existence or comparison | Separate the employee condition from the manager lookup |
| Put `COUNT` in the original `WHERE` | That filter acts before grouping | Use `HAVING` or filter a summary result |
| Use `UNION` when repeats represent separate contributions | Removes data needed by the count | Use `UNION ALL` for both roles of each friendship |
| Rely on union branch order or inner sorting for final display | Final result order is not guaranteed by those alone | Apply final `ORDER BY` when order matters |

Debug a non-correlated subquery by running it alone: inspect its columns, number of rows, duplicates, and NULLs. For a correlated subquery, take one known outer row and temporarily substitute its key value. For example, test `WHERE DepartmentID = 10` before restoring `inner_employee.DepartmentID = e.DepartmentID`.

Then manually evaluate the outer condition for one row that should pass and one that should fail. For salary comparisons, also check a tie. For missing matches, check an existing key, an absent key, and a NULL if the schema allows it.

## Quick revision sheet

| If the question means... | Think... |
|---|---|
| Greater than the overall average | `value > (SELECT AVG(...) ...)` |
| Equal to the maximum, including ties | `value = (SELECT MAX(...) ...)` |
| Belongs to a set of valid IDs | `key IN (SELECT key ...)` |
| At least one related record exists | `EXISTS (SELECT 1 ... WHERE related.key = outer.key)` |
| No related record exists | `NOT EXISTS (...)` |
| Greater than this row's department average | Correlated scalar subquery |
| Summarize a previously calculated result | Derived table in `FROM`, or a CTE |
| Match a location | Compare latitude and longitude as a pair |
| Choose one winner | Measure descending, tie-break ascending, then one-row limit |

**Two questions to ask before using any subquery:**

1. What shape does it return: one value, several values, several columns, or just an existence answer?
2. Does it need a value from the current outer row?

These are independent questions. A subquery can be scalar and correlated, scalar and non-correlated, or return many rows while correlated. A grouped query can also return a single row on a particular sample; choose a design that remains correct for the allowed data.
