# 16. Product catalog with category and supplier

**Difficulty:** Easy  
**Track / database:** SQL / Northwind  
**Practice status:** My revised final solution saved; viva complete after 2 questions

## Question

Using the Northwind database, produce a catalog listing for every product together with the category it belongs to and the supplier that provides it. Join `Products` to `Categories` (on `CategoryID`) and to `Suppliers` (on `SupplierID`).

Return exactly these three columns:

- `ProductName`: from `Products`.
- `CategoryName`: from `Categories`.
- `SupplierName`: the supplier's `CompanyName`.

Return **one row per product**. Sort the result by `ProductName` **ascending**.

**Expected output:** `ProductName`, `CategoryName`, `SupplierName` · 77 rows · order matters.

Source: [PrepNPlaced SQL practice](https://www.prepnplaced.com/data-practice), “Product catalog with category and supplier”.

## My solution

### First attempt

```sql
select Products.ProductName as ProductName , Categories.CategoryName as CategoryName , `Suppliers`.SupplierName as SupplierName
from `Categories`
full join `Products` on `Products`.CategoryID = `Categories`.CategoryID
full join `Suppliers` on `Products`.SupplierID = `Suppliers`.SupplierID
order by `ProductName` asc
```

### My final solution

```sql
select Products.ProductName as ProductName , Categories.CategoryName as CategoryName , Suppliers.CompanyName as SupplierName
from Categories
join Products on Products.CategoryID = Categories.CategoryID
join Suppliers on Products.SupplierID = Suppliers.SupplierID
order by ProductName asc
```

I explicitly confirmed this revised query as my final answer. Repeated spacing was normalized without changing my logic or starting table.

## What I learned

Review feedback and revision status:

- The join conditions use the relationships specified in the prompt, and the sorting matches the requested product-name order.
- `Suppliers.SupplierName` is not a column in the supplied schema. I corrected the source to `Suppliers.CompanyName`, keeping `SupplierName` as the output alias.
- `FULL JOIN` retains unmatched rows from both sides. It can therefore include categories or suppliers without a product, adding rows beyond the requested one-row-per-product catalog. No such extra rows have been observed in an executed result; this is feedback on the join's behavior.

Short explanation supplied at my request: matching rows in a join means matching the specified IDs, not finding identical entire records. When each product has a matching category and supplier, inner joins can retain every product and attach the corresponding names. A full join also retains categories and suppliers with no product, potentially producing rows with a missing product name. “One row per product” describes what each output row represents; it does not itself require a full join. This explanation is interviewer feedback. My subsequent final query applies `JOIN` in both places; plain `JOIN` means `INNER JOIN` here.
