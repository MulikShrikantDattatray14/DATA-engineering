# 3. Track count per media type

**Difficulty:** Easy  
**Track / database:** SQL / Chinook  
**Practice status:** Final solution shared; final viva pending; execution not verified

## Question

Count how many tracks exist for each media type in the Chinook catalog by joining `Track` to `MediaType`.

Return exactly two columns:

- `MediaType` — the media type name (`MediaType.Name`).
- `TrackCount` — the number of tracks of that media type.

Sort by `TrackCount` in **descending** order; break ties by `MediaType` ascending.

**Expected output:** `MediaType`, `TrackCount` · 5 rows · order matters.

Source: [PrepNPlaced SQL practice](https://www.prepnplaced.com/data-practice), “Track count per media type”.

## My thinking process

- I chose `GROUP BY` because the question asks how many tracks exist for each media type.
- I chose an `INNER JOIN` because I want matching rows from the two tables. I initially described it as filtering columns, then identified `SELECT` as the clause that chooses the output columns.
- I initially suggested joining on `Name`, then corrected my choice to `MediaTypeId` and used it in my second attempt. In my final query, I added the joined table and `ON` before the matching condition.
- I identified `MediaTypeId` as the value my groups should be based on and removed `COUNT` from `GROUP BY` in my third attempt. In my final query, I qualified the grouping column as `MediaType.MediaTypeId`.

## My solution

### My final solution

I shared this as my final solution. Only whitespace and line breaks have been adjusted for readability; my SQL is preserved.

```sql
select MediaType.Name as MediaType , count(TrackId) as TrackCount
from Track
join MediaType on Track.MediaTypeId = MediaType.MediaTypeId
group by (MediaType.MediaTypeId)
order by TrackCount desc , MediaType asc
```

## What I learned

- `SELECT` determines which columns appear in the final result. I identified this when clarifying my original explanation of `INNER JOIN`.
- Clarification from the review: `INNER JOIN` matches rows according to the join condition; choosing output columns is the role of `SELECT`.
- Matching column names alone does not establish a relationship. I identified `MediaTypeId` as the key connecting `Track` and `MediaType` after reconsidering `Name`.
- `GROUP BY` defines the groups, while `COUNT` calculates a count within each group. I chose `MediaTypeId` as the grouping key after reviewing my use of `COUNT` inside `GROUP BY`.
- Debugging guidance after my reported syntax error: my earlier `JOIN` line put the comparison immediately after `JOIN`. The join needs a table name followed by `ON` before the comparison. I applied this correction in my final query.
- Review guidance after my reported ambiguous-column error: both `Track` and `MediaType` contain `MediaTypeId`. A bare reference does not tell SQL which table's column to use. I applied the `table_name.column_name` form to the grouping column in my final query.

### Review notes after comparing the supplied reference

- My query uses the same join relationship, output aliases, and sorting as the reference. Short table aliases in the reference are a naming convenience.
- My query groups by media type ID, while the reference groups by media type name. Grouping by ID keeps separate media type records separate; grouping by name combines records with the same name. The groupings agree when each name corresponds to a single media type ID. That data condition has not been independently checked here.
- My query uses `COUNT(TrackId)`, while the reference uses `COUNT(*)`. My explanation of my own count expression remains pending in viva question 5; supplying the reference does not count as my answer.
- Correction to the supplied explanation: removing `GROUP BY` while retaining `COUNT` does not normally return one row per track. An aggregate query without `GROUP BY` treats the input as one group; selecting the ungrouped name alongside the count may be rejected or produce a non-group-specific name, depending on the SQL engine.
- Joining before aggregation is not automatically the fastest approach. No query-plan or performance comparison was conducted here.
